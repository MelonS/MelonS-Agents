## Findings

- **[medium]** CURRENT-ALERT.md stale — false-positive DRIFT_DETECTED signal in HEAD — `docs/audit/CURRENT-ALERT.md`
  Evidence: `git show HEAD:docs/audit/CURRENT-ALERT.md` shows **Verdict: DRIFT_DETECTED**
  generated 2026-05-16 17:09:55 KST, referencing two HIGH findings in `2026-05-16-contract.md`:
  (1) `scripts/contact-sheet.sh:9` hardcoded path and (2) uncommitted working-tree fixes.
  Both findings were resolved in commit `05a14a9` (17:10:37 KST, 42 seconds later).
  `git log --oneline -- 'docs/audit/CURRENT-ALERT.md'` shows `05a14a9` as the most recent
  commit touching this file — it re-added the file as a **new file** (diff shows
  `new file mode 100644`) alongside the fixes, rather than deleting it.
  The correct workflow is: fix → re-run `./scripts/audit-run.sh` → CLEAN verdict →
  wrapper auto-deletes the alert → commit the cleared state.  Instead, the stale alert
  generated at 17:09 was bundled into the fix commit at 17:10 without a re-run.
  `docs/audit/README.md` line 41 states the file "Exists **iff** the most recent audit
  verdict is non-CLEAN" — this invariant is broken.  Every new session will read the false
  alarm before the roadmap, per `CLAUDE.md` session-start protocol.
  The roadmap "Now" item 3 acknowledges the alert exists ("Check `docs/audit/CURRENT-ALERT.md`
  — if present, address the audit finding before picking up the next pilot") but the session
  was not able to clear it because it requires a re-run of the auditor.
  Suggested fix: Run `./scripts/audit-run.sh contract` (this audit) to produce a new CLEAN
  or DRIFT_DETECTED report; if CLEAN, the wrapper will auto-delete CURRENT-ALERT.md; commit
  the cleared state as a standalone commit referencing the lifecycle protocol.

- **[low]** §8 — hardcoded machine-specific absolute path in committed documentation comment — `scripts/statusline.sh:17`
  Evidence: `scripts/statusline.sh` line 17 reads:
  `"command": "/Users/melons/ai/scripts/statusline.sh"`
  This appears inside a comment block showing example `~/.claude/settings.json` configuration.
  §8 states "never hardcode `~/...`"; `/Users/melons/ai/...` is the literal expansion of that
  path on this machine.  Although the instance is in a comment (not executable logic), it is
  in committed content and would silently give an incorrect example path on any machine swap.
  No prior audit flagged this line; it pre-dates the operator contract.
  Suggested fix: Replace `/Users/melons/ai/scripts/statusline.sh` with
  `<absolute-path-to-repo>/scripts/statusline.sh` or add a note that the path must be
  substituted for the local repo root (e.g., `$(git rev-parse --show-toplevel)/scripts/statusline.sh`).

- **[low] carry-forward** §8 tension — `/opt/homebrew/bin/claude` in launchd-PATH fallback list — `scripts/audit-run.sh:40`
  Evidence: `scripts/audit-run.sh` lines 38–41 iterate a candidate list to locate the
  `claude` CLI under launchd's minimal PATH:
  `"$HOME"/.nvm/versions/node/*/bin/claude`, `"$HOME"/.local/bin/claude`,
  `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`.
  §8 prohibits hardcoding `/opt/homebrew/...`.  The surrounding comment (lines 31–35)
  explains the rationale: "under launchd the PATH is minimal and does not include nvm-managed
  node bins."  This is structurally identical to the `agents/lib/env.sh` keg-only ffmpeg
  discovery pattern, which the prior audit (2026-05-16) explicitly deferred as a
  "documented exception" at [low] severity.  Checked for the first time in this audit.
  Suggested fix: Add an inline comment citing §8 and labelling this as a launchd-specific
  exception (same wording as the env.sh keg-only comment), so future audits can classify
  it without re-reading the context.

- **[info] carry-forward** §5 — no formal user-confirmation marker token — `docs/operator-contract.md:85–89`
  Evidence: §5 requires "explicit user OK" before editing `.claude/agents/*.md` or
  `agents/*.md` but the rule text does not define what commit-message text constitutes an OK.
  The two commits touching `.claude/agents/*.md` (`af9857f`, `27a8c86`) carry implicit
  user-initiation evidence in their bodies (`af9857f`: "User requested a project-wide

  not drift").
  Suggested fix: Define the marker in §5, e.g., "Commit message must include a
  `Requested-by: user` footer line to record that explicit user approval was obtained."

- **[info]** §11 daily-report naming convention drift — `docs/daily/`
