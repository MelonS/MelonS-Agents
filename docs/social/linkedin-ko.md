# LinkedIn 한국어 스니펫 — 일일 진행 포스트용

운영자가 LinkedIn에서 하루 1-2회 이 프로젝트의 진행을 공유함.  이 파일은 매 마일스톤마다 *그대로 또는 부분 발췌해서 복붙*할 수 있는 한국어 스니펫 모음.

작성 톤 (operator-contract.md `writing_tone`):
- 중립적·기술적 — 마케팅 형용사 없음, 개인 경력 언급 없음
- 구체적 수치 > 모호한 주장
- 이모지 없음
- 짧은 단락 — LinkedIn 모바일 가독성

매 스니펫 구조:
1. 후크 1줄 ("see more" 클릭 유도)
2. 맥락 1-2단락
3. 무엇을 했는지 / 구체 수치
4. 무엇을 배웠는지 / 다음 단계
5. 레포 링크
6. 해시태그

## #2 — Tier-1 라우팅 교훈 (오늘의 가장 비싼 학습)

```
오늘 가장 비싼 학습 — "처음부터 클로드로 했어야지."

운영자가 4개 파일럿 영상을 보고 한 말입니다.

설계 원칙은 단순했어요. "API 비용 = 0원으로 운영 가능해야 한다."
그래서 모든 단계 (스크립트 생성, 음성 합성, B-roll 선택, 렌더링)
를 로컬 (llama3.2:3b, whisper.cpp, Kokoro TTS, ffmpeg)로만 돌렸습니다.

결과: 첫 5초 후크가 약해서 시청자가 이탈할 수밖에 없는 스크립트.
"What if..." 같은 진부한 도입부, 사실 충돌 (수소가 몸의 10%? 60%?).

진짜 문제는 "Tier 2 (로컬) = 기본값"이라는 규칙을 *모든* 단계에
일괄 적용한 거였습니다. 트랜스크라이브·렌더링처럼 반복적·기계적
단계는 로컬이 맞지만, 스크립트 생성처럼 일회성·창작 단계는
호출당 500토큰 (구독 할당량 기준 무시 가능 수준)인데도 품질이
다음 60초 전체를 좌우합니다.

스크립트 단계만 Claude Sonnet으로 라우팅했더니 같은 토픽의 점수가
32/50 → 44/50으로 올랐습니다. 후크 +6, 사실 일관성 +3.

교훈: "비용 최적화" 규칙은 *어디에 적용하느냐*가 더 중요했습니다.
모든 곳에 적용하면 그건 최적화가 아니라 천장입니다.

자세히: github.com/MelonS/MelonS-Agents/blob/main/docs/cost-model.md

#멀티에이전트 #ClaudeCode #AIPipeline #LLM #DevLog
```

## #3 — L1 + L2 반응형 감사 자동화

```
"드리프트 (Drift)"는 멀티에이전트 시스템의 조용한 부패입니다.

매일 03:00시에 한 번씩 돌던 감사 에이전트가 있었습니다.
어제 밤 11시에 코드가 커밋되면, 다음 새벽 3시까지 4시간 동안
운영자 컨트랙트와 실제 코드가 따로 노는 상태였습니다.

오늘 이 간극을 두 레이어로 닫았습니다.

L1 — git post-commit 훅: 드리프트 위험 경로 (agents/,
.claude/agents/, config/, CLAUDE.md, operator-contract.md)를
건드린 모든 커밋이 끝나면 즉시 백그라운드에서 audit 발화. 30초
안에 결과 보고. 검증: 두 차례 실전 발동, 모두 CLEAN.

L2 — 15분 간격 미션 이상 감지: 새 블로커 파일 또는 QA-FAIL
클러스터를 잡으면 audit 발화. 정상 상태에서는 파일 읽기만 하고
끝나는 (token 0) no-op.

L3 (기존) — 매일 03:00시 전체 감사 baseline 유지.

세 레이어 시스템: 즉시 (L1) → 빈번 (L2) → 기준점 (L3).
설계 패턴은 흔히 말하는 Observer가 아니라 Reactor + Hook —
이 레포의 파일 기반 통신 방식과 정확히 맞습니다.

자세히: github.com/MelonS/MelonS-Agents/blob/main/docs/audit/README.md

#멀티에이전트 #ClaudeCode #DevOps #감사자동화 #DevLog
```

## #4 — 점수표 자체평가 (썸네일만으로 보이지 않는 진화)

```
"썸네일만 보이니깐 머하는건가 싶기도."

운영자 피드백 — 영상 만들고 있는데 결과물의 진화가 안 보임.

캡쳐 한 장으로는 v4 → v5 → v6의 진행을 알 수 없습니다.
"좋아 보인다"도 "어제보다 좋다"도 객관적 지표가 아닙니다.

그래서 5축 점수표를 만들었습니다.

1. 후크 (Hook) — 첫 5초가 다음 5초를 벌어주는가
2. 영상-자막 매칭 — B-roll이 말하는 내용과 시각적으로 맞는가
3. 자막 가독성 — 단일 라인, 박스 겹침 없음
4. 사실 일관성 — "수소 10%? 63%?" 같은 자기모순 없음
5. 마감 — TTS 톤, 화면 채움, 워터마크

투명성: 점수는 시청자 패널이 아니라 제 자체평가입니다. 실제
플랫폼 시청 데이터가 들어오기 전까지의 *구조화된 진행 신호*로만
사용합니다.

결과:
- Hittites EN: v4 26/50 → v5 32/50 → v6 44/50
- Hydrogen EN: v5 28/50 → v6 43/50

단순한 "잘 됐다"가 아니라 어디서 진행됐는지가 차원별로 보입니다.
v5→v6 상승폭 대부분이 후크 + 사실 일관성 — 운영자가 지적한
바로 그 차원이었습니다.

차트 + JSON 원본 데이터 + 차원 정의 다 레포 공개.

자세히: github.com/MelonS/MelonS-Agents/blob/main/docs/pilots/scorecard.md

#멀티에이전트 #자체평가 #DevLog #쇼츠
```

## #5 — 단일 라인 자막 강제 (작지만 시각적인 픽스)

```
"자막 박스가 겹치면 너무 이상해 보임."

운영자가 4개 파일럿 영상을 보고 한 첫 번째 지적.

쇼츠 자막은 모바일에서 거의 *유일한* 정보 채널입니다 (대부분
음소거 시청). 그런데 libass의 BorderStyle=3 (라인당 불투명 박스)
설정 + 2줄로 줄바꿈된 자막이 만나면, 인접한 큐의 박스가 서로
스쳐 지나가면서 "오버랩" 처럼 보입니다.

픽스: 새 후처리 단계 (scripts/split-long-captions.py)를 캡션
교정과 ASS 렌더 사이에 끼웠습니다.

- 28자 초과 큐를 자연 구두점 위치 (쉼표, 마침표, em-대시)에서
  먼저 분할 — 음성 휴지와 일치해서 자연스러움
- 그래도 긴 청크는 그리디 단어 분할
- "a/an/the/은/는" 같은 1자 연결어가 청크 끝에 고아처럼 남으면
  다음 청크 앞으로 이동
- 1초 미만 큐는 이전 큐에 병합 (sub-second 깜빡임 방지)

결과: 동일 스크립트·동일 B-roll로 v5 재렌더만 했는데 자막
가독성 점수가 4/10 → 9/10. 만든 코드는 154줄 파이썬 + bash
와이어링 18줄.

작은 픽스, 큰 인지적 효과.

자세히: github.com/MelonS/MelonS-Agents/blob/main/scripts/split-long-captions.py

#멀티에이전트 #DevLog #쇼츠 #모바일UX
```

## 사용 팁

- 한 번에 하나만 올리는 게 LinkedIn 알고리즘에 좋음 (24시간 간격 권장)
- 첫 줄이 "see more" 트리거 — 그 한 줄에 후크가 살아 있어야 함
- 길어 보이지만 LinkedIn은 "see more" 클릭으로 확장 — 본문이 길어도 ok
- 해시태그는 3-5개가 알고리즘 친화적
- 댓글로 토론 유도하는 질문 ("어디서 비슷한 라우팅 문제 겪으셨나요?") 추가하면 engagement 상승

## 새 마일스톤 추가 방법

새 큰 작업이 끝날 때마다 이 파일 맨 위 ("## #N — ...") 에 새 스니펫 추가.
운영자가 LinkedIn 포스트 작성 시 이 파일을 열어서 가장 위 스니펫을 복붙 → 게시 → 그 스니펫은 사용 표시 (`<!-- 사용 2026-MM-DD -->` 주석 추가) 하면 중복 방지됨.
