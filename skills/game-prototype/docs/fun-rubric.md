# 재미 루브릭 — 심사자의 10분을 100점으로

**계기 (2026-08-02 운영자)**: *"유저의 재미를 점수화 시켜서 재미에 대한 점수를
올려야 할 거 같아."*

이 레포는 톤(`check-art-tone.py`)과 에셋 드리프트(`check-asset-drift.py`)를 이미
수치로 판정한다.  **재미만 감상으로 남아 있었다.**  그 대가가 컸다 — 같은 문제를
세 번 다른 말로 진단했다:

| 날짜 | 운영자 표현 | 실제로 같은 것 |
|---|---|---|
| 2026-07-30 | "영상 100점 만점에 2점" | 사건이 없다 |
| 2026-07-31 | "뭐 하고 있는건지 모르겠음" | 활력·읽힘이 없다 |
| 2026-08-02 | "10분간 숫자가 안 움직인다" | 진행감이 없다 |

셋 다 한 화면의 서로 다른 면이다.  잴 수 있으면 한 번에 보이고, **무엇을 고쳤을 때
올라갔는지도 보인다.**

---

## 왜 '10분' 인가

게임잼·페스티벌 심사 통설은 엔트리당 5~15분, 첫인상은 ~5분이다.  콜로니심은
수십 시간짜리 장르지만 **심사자는 첫 10분만 본다.**  30시간 뒤에 재미있는 것은
이 루브릭에서 0점이다 — 심사자가 볼 수 없기 때문이다.

이건 장르를 배신하는 게 아니라 **제출물의 제약을 인정하는 것**이다.  긴 호흡의
재미는 그대로 두고, 그 재미의 *예고편*이 10분 안에 보이게 만든다.

---

## 축과 배점

| 축 | 배점 | 질문 | 만점 기준 (10분) |
|---|---:|---|---|
| **진행감** | 30 | 마을이 눈에 띄게 자라는가 | 목표 +3 / 구조물 +6 / 가치 ×2.5 |
| **사건** | 25 | 손대지 않아도 무슨 일이 일어나는가 | 8건, 최장 침묵 90초 이하 |
| **활력** | 20 | 주민이 놀고 있지 않은가 | 유휴 15% 이하, 동시 활동 3종 |
| **긴장** | 15 | 위협이 오고 **해소되는가** | 발생→해소 1사이클 |
| **다양성** | 10 | 서로 다른 활동이 몇 가지 보였나 | 8가지 |

**배점 근거는 운영자가 실제로 지적한 순서다.**  두 번의 탈락 판정 사유가
진행감(30)과 사건(25)이었고, 그 다음이 활력(20)이었다.  취향으로 정한 가중치가
아니다.

**긴장 축의 비대칭**: 위협이 발생만 하고 해소되지 않으면 절반만 준다.
해소 없는 위협은 스트레스지 재미가 아니다.

## 어떻게 재는가

```
게임          FunTelemetry.cs      5초마다 상태를 JSONL 로 남긴다 (-funscore 인자)
채점          scripts/fun-score.py  루브릭을 적용해 100점으로 환산
측정 시나리오  repro-scenarios/_measure-judge-10min.json
```

**사건은 훅이 아니라 상태 변화에서 유도한다.**  시스템마다 콜백을 박으면 훅이
늘 때마다 계측이 갈라진다(이 레포의 반복 함정).  목표 수·구조물 수·연구 수·
적 수의 증감을 보고 사건을 읽으므로, 계측 대상이 늘어도 파일 하나만 본다.

**루브릭을 게임 안에 두지 않는 이유**: 루브릭은 자주 바뀌는데 게임은 자주
빌드할 수 없다.  게임은 **사실만** 남기고 해석은 밖에서 한다.  덕분에 과거
세션의 JSONL 을 새 루브릭으로 다시 채점할 수도 있다.

### 실행

```bash
EXE=skills/game-prototype/builds/day-X-<date>/PawnSim.exe
"$EXE" -autostart -repro skills/game-prototype/repro-scenarios/_measure-judge-10min.json \
       -funscore G:/ai/_fun.jsonl -logFile G:/ai/_fun.log
python skills/game-prototype/scripts/fun-score.py G:/ai/_fun.jsonl
```

## 이 루브릭이 하지 않는 것

- **장기 밸런스** — 심사창 밖이다.  별도 문서(`balance-parity-*.md`)가 본다.
- **아트 품질** — TA 게이트와 `check-art-tone.py` 담당.
- **주관적 '손맛'** — 잴 수 없는 것을 재는 척하지 않는다.  루브릭이 만점이어도
  재미없을 수 있다.  다만 **루브릭이 낮으면 확실히 재미없다** — 그 하한을 막는
  도구다.

| 2026-08-07 | 56.8 | 16.2/30 | 17.1/25 | 13.4/20 | 0.0/15 | 10.0/10 | **같은 게임인데 22점 흔들림** |
| 2026-08-07 | **78.1** | 20.5/30 | 19.3/25 | 13.3/20 | **15.0/15** | 10.0/10 | 계측 3종 수정 후 — 신뢰 가능 |

### 같은 게임을 두 번 재서 78.7 과 56.8 이 나왔다

22점 차이의 원인은 게임이 아니라 **계측**이었다.  세 가지가 겹쳐 있었다.

**① 순간 상태를 폴링으로 잡으려 했다.**  살아있는 적 수를 5초마다 셌는데,
3배속에서 산적 2명은 주민 6명에게 폴링 간격보다 빨리 제압된다.  로그엔
`RAID #1 bandits=2` 가 있는데 `threats>0` 표본이 한 번도 안 잡혔다.
→ 누적 카운터로.  **누적은 놓칠 수 없다.**

**② 습격의 30% 는 산적이 아니라 광기 떼다.**  계측은 `BanditEnemy` 만 셌으니
그 30% 는 통째로 '위협 없음' 이 됐다.  실측 로그에는 `MANHUNTER boars=3` →
`manhunter cleared` 로 **위협이 오고 격퇴까지 정상 동작**했는데 점수는 0 이었다.

**③ 격퇴를 셀 방법이 없었다.**  `BanditEnemy.KilledCount` 는 산적만 센다.
→ `AIDirector.ThreatsCleared` (습격·광기 떼 공통).

> 교훈: **루브릭보다 계측을 먼저 의심하라.**  점수가 흔들리면 게임이 흔들린 게
> 아니라 자가 흔들린 것일 수 있다.  같은 입력에 같은 값이 나오는지 —
> 재현성이 계측의 최소 조건이고, 그걸 확인하지 않은 채 78.7 을 '개선' 으로
> 보고할 뻔했다.

### 2026-08-07 — 46.7 → 78.7

바뀐 것은 하나다: **첫 습격이 실제로 온다.**  긴장 0→15 는 물론이고 사건도
7.2→19.9 로 뛰었다 (습격 전후로 경고·교전·격퇴 알림이 줄줄이 붙는다).
최장 침묵 475초 → 185초.

**여기까지 오는 데 다섯 번 헛짚었다.**  기록해 둘 값어치가 있다:

| 시도 | 무엇을 고쳤나 | 결과 |
|---|---|---|
| 1 | 코드 `RaidGraceDays` 2 → 1 | 0건 |
| 2 | `FirstRaidWaitDays = 0.8` 신설 | 0건 |
| 3 | **씬에 굳어 있던** `RaidGraceDays: 2` | 0건 |
| 4 | 시각 지터가 0.8일을 1.05~1.72일로 밀던 것 | 0건 |
| 5 | **측정에 쓴 exe 가 5일 전 빌드였다** | ✅ |

5번이 나머지 넷을 전부 가리고 있었다.  빌드 폴더가 날짜 스탬프(`day-X-<날짜>`)라
날짜가 바뀌면 새 빌드는 새 폴더로 나가는데, 하드코딩한 경로가 옛 폴더를 계속
가리켰다.  **빌드는 성공하고 측정도 정상 종료한다 — 그냥 어제 게임을 잰다.**

1~4 는 전부 실제 결함이었고 고친 것이 맞다.  다만 그 사실을 **5를 고치기 전에는
알 수 없었다.**  그래서 도구를 만들었다 — `latest_build.py` 가 경로를 돌려주고
`--check` 로 소스보다 낡았는지 판정한다.  경로를 손으로 적을 수 없게 하는 것이
메모보다 확실하다.

### 다음 목표: 활력 (−7.2)

활동 분포가 원인을 바로 알려줬다:

```
수면 41.1% / 떠도는중 34.0% / 연구 8.3% / 산딸기 운반 5.3% / 식사 2.3% ...
```

유휴 35% 의 대부분이 **수면**이다.  10분에 게임 2일이 지나니 밤이 두 번 오고
그동안 전원이 잔다 — 정상이다.  즉 이건 게임 결함이 아니라 **계측 결함**이었다.
자는 주민을 유휴에서 분리했다.  남는 '떠도는중' 이 진짜 유휴다.

### 2026-08-02 첫 측정에서 읽은 것

```
진행감  목표 +2 / 구조물 +0  / 가치 x2.66
사건    3건 (0.3/분), 최장 침묵 475초
활력    유휴 34%, 동시 활동 1.3종
긴장    위협 발생 0 / 해소 0
다양성  활동 14가지
```

축마다 원인이 바로 특정됐다 — 이게 루브릭을 만든 이유다.

| 축 | 잃은 점수 | 특정된 원인 |
|---|---:|---|
| 사건 | −17.8 | 계측이 디렉터 이벤트를 안 세고 있었다 (측정 결함) + 큰 이벤트 주기가 창 밖 |
| 긴장 | −15.0 | `RaidGraceDays` 는 하한일 뿐, 실제 일정은 `RaidIntervalDays(3)±1일` → 첫 습격이 **2.9~4.9 게임일**(3x 에서 실제 16~27분)로 심사창 밖 |
| 진행감 | −13.5 | 자동 일감이 자원만 캐고 **짓지는 않는다** (구조물 +0) |
| 활력 | −7.0 | 유휴 34% — 원인 미특정 → 활동 분포 계측을 추가해 다음 측정에서 확인 |
| 다양성 | 0 | 만점.  더 손댈 필요 없음 |

**'다양성 만점'이 중요한 정보다.** 활동 종류는 이미 충분하니 여기에 시간을 쓰면
안 된다는 뜻이다 — 루브릭이 없었으면 "더 다양하게 만들자"로 갔을 수 있다.
