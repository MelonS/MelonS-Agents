## 0. 한 줄

**직접 조종하지 않는 게임을, 직접 코딩하지 않고 만들었다.**

이 문서는 그 두 문장이 같은 구조라는 것을 보인다.

---

## 1. 두 층은 같은 구조다

PawnSim 은 조선 산골 마을을 키우는 간접 조작 시뮬레이션이다.  플레이어는 유닛을
직접 조종하지 않는다 — **일감을 지정**하면 주민이 각자의 작업 우선순위·스킬·현재
니즈로 무엇을 언제 할지 스스로 판단한다.

이 게임은 **같은 방식으로 만들어졌다.**  제작자는 코드를 직접 쓰지 않는다 —
방향을 지정하면 역할별 에이전트가 각자의 정책으로 판단해 만든다.

```
┌─ 게임 안 ─────────────────────────────┐   ┌─ 게임 밖 ─────────────────────────────┐
│ 플레이어                               │   │ 제작자(디렉터)                         │
│   ↓ "무엇을"만 지정                     │   │   ↓ "무엇을"만 지정                    │
│ 작업 우선순위 그리드 (6인 × 9직종)      │   │ 정책 (config/policies.yaml)            │
│   · 0=비활성 1~4=우선순위               │   │   · 자율 범위 / 머니 파이어월          │
│   · 스킬에서 기본값 유도                │   │   · 로직 변경은 승인 필요              │
│   ↓                                    │   │   ↓                                   │
│ PawnUtilityAI                          │   │ 역할 에이전트                          │
│   · 8개 워커의 효용 집계 → 행동 선택    │   │   · planner / artist / programmer      │
│   · 니즈·무드·스케줄이 선택에 개입      │   │   · qa / ta / auditor                 │
│   ↓                                    │   │   ↓                                   │
│ "누가 언제 어떻게"는 에이전트가 결정    │   │ "누가 언제 어떻게"는 에이전트가 결정   │
└───────────────────────────────────────┘   └───────────────────────────────────────┘
```

두 층이 **같은 문장으로 기술된다**는 것이 이 제출물의 논점이다.

## 2. 제작 구조 — 무엇이 무엇을 판단하는가

### 2.1 역할 분리

에이전트 정의는 `.claude/agents/*.md` 에 있고, 각각 도구 권한과 판단 범위가 다르다.
게임 제작에 실제로 쓰인 것:

| 에이전트 | 판단하는 것 | 도구 |
|---|---|---|
| `game-designer` | 시스템·메카닉·조작 | 읽기/쓰기 |
| `game-programmer` | 스크립트 구현 | 읽기/쓰기/편집/실행 |
| `game-build-engineer` | 씬 조립·빌드 파이프라인 | 읽기/쓰기/편집/실행 |
| `game-qa` | 빌드 실행 → 스크린샷 → 판정 | 읽기/실행 |
| `ta` | **아트 자산의 미적 품질 채점** (제작자와 분리된 눈) | 읽기/실행 |
| `auditor` | 저장소 전반의 드리프트 감사 (읽기 전용) | 읽기/실행 |

핵심은 `ta` 와 `auditor` 다.  **만드는 주체와 판정하는 주체를 분리**해야 "만든
사람이 자기 결과물을 좋게 보는" 편향이 끊긴다.

### 2.2 판정은 사람의 눈이 아니라 게이트가 한다

지각적 주장("톤이 이상하다")은 재현되지 않는다.  그래서 **수치로 바꿔 게이트에
넣는다.**  현재 가동 중인 것:

| 게이트 | 무엇을 잡나 |
|---|---|
| `check-art-tone.py` | 팩 톤 서명 이탈 — 외곽선 휘도·색 수·채도·명도 |
| `check-asset-refs.py` | 끊긴 스프라이트 참조 (조용히 안 그려짐) |
| `check-sprite-ppu.py` | 등록 PPU ≠ `.meta` (엉뚱한 크기로 들어감) |
| `check-font-coverage.py` | 폰트에 없는 문자 (빈칸으로 그려짐) |
| `spec-sync.py` | 기획서 ↔ 구현 드리프트 (유령 컴포넌트·그림자 상수·문서 수치) |
| `repro_all.py` | 재현 시나리오 24종 (기능 회귀) — 측정 전용 `_` 접두 22종은 게이트 제외 |
| `UiSweepQA` | **모든 버튼을 눌러 보고 반응 없는 것** |

넷은 공통점이 있다 — **빌드는 성공하는데 화면만 잘못되는** 종류를 잡는다.
컴파일·테스트가 구조적으로 못 보는 사각지대다.

### 2.3 게이트는 자기 임계를 검증한다

임계값을 사람이 감으로 정하면 그 게이트는 신뢰할 수 없다.  그래서 각 게이트는
`--self-test` 로 **기준선이 자기 임계를 통과하는지** 확인한다.

- `check-art-tone --self-test` → 팩 원본 12종이 전부 PASS 해야 한다 (12/12)
- `spec-sync --self-test` → 알려진 사고 4종을 재현해 탐지기가 실제로 잡는지 확인

한 번도 빨간불을 본 적 없는 게이트는 게이트가 아니다.

## 3. 증거 — 게이트가 실제로 잡은 것

주장이 아니라 사건으로 적는다.  전부 커밋 이력에 남아 있다.

### 3.1 톤 게이트가 사람 눈을 이겼다

`tswords_v1` LoRA 로 뽑은 침엽수 3시드가 컨택트시트에서는 "괜찮아 보였다."
게이트는 상대휘도 **0.051~0.058** 로 팩 최저(0.096)보다 어둡다고 FAIL 시켰다.
프롬프트의 `dark green` 이 원인이었고, `sunlit green` 으로 고쳐 0.144 로 통과.
**게이트가 없었으면 그대로 반입됐다.**

같은 게이트가 더 큰 것도 잡았다 — 생성물의 **색 수가 405~1022** 였다(팩은 4~9).
512px 생성물을 96px 로 줄이면서 중간색이 수백 개 생기고 1px 아웃라인이 평균에
먹힌 것이다.  확대해서 보면 잘 나왔는데 **팩과 다른 종류의 이미지**가 돼 있었다.
복구는 3단이고 순서가 고정이다: 채도 정렬 → 팔레트 양자화 → 팩 아웃라인 확정.

### 3.2 "관찰"이 틀렸던 것을 실측이 잡았다

절차 드로잉 생성기가 아웃라인 색으로 웜브라운 `(62,42,34)` 를 쓰며 주석에
"팩 관찰로 뽑은 색"이라 적어 두었다.  팩 12종의 최암부를 **실제로 재보니**
쿨 네이비 `(22,28,46)` 였다.  휘도로 0.028 vs 0.012 — 절차 가구가 팩 옆에 놓이면
아웃라인만 옅게 떠 보였다.  상수 하나를 고치자 절차 아트 17건이 일괄 정합됐다.

### 3.3 정본을 가리는 그림자 상수

`SceneSetup.cs` 에 지역 상수 `const int MAP_HALF = 20` 이 있었고, 그것이 정본
`TerrainLayout.MAP_HALF = 45` 를 가린 채 나무 배치에만 전달되고 있었다.
맵이 40×40 → 60×60 → 90×90 으로 두 번 커지는 동안 이 값만 20 에 남아,
**맵 면적의 56%(중심거리 30~45)에 나무가 0그루**였다.  빌드도 게이트도 통과했다.
`spec-sync` 가 이 계열을 잡도록 만들어졌다.

### 3.4 UI 스윕이 잡은 죽은 버튼

콜로니스트를 선택하지 않고 `징집` 을 누르면 **완전 무반응**이었다 —
UI·선택·카메라 어느 것도 변하지 않았다.  기능은 정상이고 전제(선택)가 빠졌을
뿐인데, 심사자가 누르면 고장난 버튼으로 읽힌다.  안내 토스트를 붙여 해소.

### 3.5 게이트 자체의 결함을 게이트가 드러냈다

- 톤 게이트의 채도 **하한**이 돌·광맥·무덤을 전부 오탐했다.  바위가 회색인 것은
  톤 위반이 아니다 — 기준선(팩 12종)에 무채색 자산이 없어 자가검증만으로는
  안 드러났다.  하한을 제거했다.
- UI 스윕은 판정 지표를 **네 번** 갈아엎고서야 정확해졌다 (픽셀 diff → 텍스트
  개수 → 인스턴스 ID → 내용만 → **내용+위치 + Graphic 수 + 월드 지문**).
  세 번째 시도에서는 멀쩡한 초상화 버튼을 "죽었다"고 보고했다 — 효과가
  월드 공간(선택 링·카메라)이라 UI 계층에 흔적이 없었기 때문이다.
- UI 스윕이 **사용자 설정을 오염**시켰다.  모든 버튼을 누르므로 설정의 팔레트
  토글도 눌렀고, 그게 `PlayerPrefs` 에 저장돼 UI 테마가 영구히 바뀌었다.
  스냅샷·원복을 넣었다.

이 세 건은 실패가 아니라 이 문서의 논점이다 — **자동 판정을 도입하면 판정기
자체가 검증 대상이 된다.**

### 3.6 게이트 플레이크의 근본 원인

재현 시나리오가 간헐적으로 실패했다.  원인은 게임플레이 코드가
`UnityEngine.Random` 을 **57곳**에서 쓰는데 `Random.InitState` 호출이 **0곳**이라,
유니티가 세션마다 시스템 엔트로피로 시드해 같은 입력에도 매번 다른 난수열이
나온 것이었다.  재현 모드에서만 시드를 고정해 스모크가 3연속 4/4 로 안정됐다
(일반 플레이는 그대로 매번 다르다 — 콜로니심은 그래야 한다).

### 3.7 초록불이 증명하지 않는 것

같은 날, 재현 시나리오 **18/18 PASS** 상태에서 공개 URL 을 브라우저로 직접 열어
보았다.  세 가지가 동시에 참이었다.

1. **배포본이 9커밋 뒤처져 있었다.**  그날 한 작업(지형 전환·SFX·스킬 탭·암반
   지대·동물 크기·타이틀 모션)이 공개 URL 에 **하나도 없었다**.  제출물의 실체는
   URL 인데, 로컬 게이트는 URL 에 대해 아무 말도 하지 않는다.
2. **인게임 캡처 도구가 죽어 있었다.**  대기가 스케일 시간(`WaitForSeconds`)이었고
   게임은 의도적으로 일시정지로 부팅하므로, 타이머가 영원히 안 흘렀다.  로그엔
   "will capture in 14s" 만 남고 파일은 안 생겼다 — **조용한 실패**.
3. **폴백이 '성공'해서 버그가 됐다.**  콜로니스트 변형 스프라이트 배정은 성공했고
   경고도 없었다.  그런데 가시 스프라이트의 주인은 다른 컴포넌트였고, 그건
   스프라이트 **이름**에서 변형 번호를 파싱한다.  이름 규약이 안 맞아 이름 해시로
   폴백했고, 시작 주민이 공교롭게 전부 같은 계열로 사상돼 **다들 똑같아 보였다**.
   각 단계는 계약을 지켰고 전체만 틀렸다.

세 건의 공통점은 **아무도 실패를 보고하지 않았다**는 것이다.  게이트는 자기가
보도록 설계된 것만 본다.  그래서 이 프로젝트는 게이트 위에 한 겹을 더 둔다 —
"운영자(=심사자)가 실제로 밟는 경로를 그대로 밟아 본다".  이번 회차에는 그것이
배포된 URL 을 브라우저로 열고, 실제로 클릭해 게임 안까지 들어가, 화면을 원본
해상도로 잘라 확대해 보는 일이었다.  거기서만 5건이 나왔다.

> 자동화의 한계는 자동화로 못 넘는다.  넘는 방법은 **판정의 층을 하나 더 두는
> 것**이고, 그 층의 기준은 언제나 "산출물을 받는 사람이 보는 것"이다.
> 상세 기록: `docs/live-verification-2026-07-29.md`.

### 3.8 안전장치가 꺼져 있으면 없는 것만 못하다

2026-07-31, 게이트를 돌렸더니 **22/22 STALE** — 한 시나리오도 실행되지 않았다.
그런데 같은 빌드로 러너를 직접 부르면 정상 실행됐다.  원인은 둘이었고 둘 다
게이트 **자신의** 버그였다.

1. 스위트가 `--build` 를 **상대 경로 그대로** 자식 프로세스에 넘겼다.  자식은 다른
   작업 디렉터리에서 돌기 때문에 그 경로가 존재하지 않는다 → 러너는 "빌드 없음"으로
   즉시 종료하고, 스위트는 그것을 STALE 로 집계한다.
2. 신선도 판정이 빌드 **디렉터리**의 mtime 을 봤다.  디렉터리 mtime 은 항목이
   추가/삭제될 때만 갱신되는데, Unity 재빌드는 기존 파일을 **제자리에서 덮어쓴다**.
   즉 같은 폴더로 두 번째 빌드를 한 순간부터 **영구 STALE** 이었다
   (실측: 컴파일 산출물 04:09 / 디렉터리 00:08).  실행 파일도 기준이 될 수 없다 —
   런처 스텁이라 코드가 바뀌어도 내용이 같으면 다시 쓰이지 않는다.  이 빌드가 담은
   코드를 대표하는 것은 컴파일된 어셈블리 하나뿐이다.

STALE 은 "실패"가 아니라 **"검증하지 않았다"** 이므로, 요약에서 빨간불로 보이지
않았다.  안전장치가 조용히 꺼진 채로 며칠이 지날 수 있었다는 뜻이다.

> §2.3 이 "게이트는 자기 임계를 검증한다"였다면, 이 건은 그 다음 질문이다 —
> **게이트가 애초에 돌기는 했는가.**  통과 개수만 세면 0건 실행도 초록으로 보인다.

### 3.9 속도를 올렸는데 산출이 줄었다

연구 진행이 느려서 속도 상수를 0.15 → 0.25 로 올렸다.  결과는 하루 24pt → **11pt**.
올렸는데 줄었으면 배정이 아니라 **체류**가 문제다.

원인은 유틸리티 AI 의 "지금 실제 작업 중인가" 판정이었다.  그 함수는 워커 컴포넌트
9종을 나열해 검사하는데, **연구는 워커 컴포넌트가 없는 유일한 작업**이라 목록에서
빠져 '유휴'로 떨어졌다.  유휴로 분류된 림은 0.8초마다 근처 타일로 배회하고, 그게
연구자를 연구대 반경 밖으로 끌어냈다 — 진행도는 반경 안에서만 쌓인다.

더 흥미로운 것은 **왜 이제야 보였는가**이다.  직전까지 진행 판정은 '연구대 반경 안의
살아있는 폰 전부'를 셌다.  그래서 배회하던 다른 림들이 우연히 점수를 채워 주고 있었고,
판정을 실제 담당자로 좁히자 가려져 있던 배회 문제가 그대로 드러났다.  수정이 버그를
만든 게 아니라 **가리고 있던 것을 걷어냈다**.

수정 후: 오후 1시 4pt → **17pt**, 첫 연구가 **첫 게임일 안에** 완료.

> 두 교훈. (a) 나열식 규칙(`if A || B || … || I`)을 쓰면 **그 목록의 예외부터
> 찾는다** — 목록은 자기가 빠뜨린 것을 알려주지 않는다.  (b) 숫자를 올렸는데 결과가
> 나빠지면 숫자를 더 올리지 말고 **전제를 의심한다**.
> 상세 기록: `docs/legibility-and-progression-2026-07-31.md`.

### 3.10 안전장치가 7주간 꺼져 있었고, 그걸 찾은 것도 에이전트였다

§3.8 은 게이트 하나가 조용히 꺼져 있던 이야기다.  더 큰 것이 뒤에 있었다.

게임은 **일시정지 상태로 부팅**한다 — 플레이어가 맵을 둘러보고 계획한 뒤 직접
시작하는 편이 이 장르에 맞기 때문이다.  그런데 이 일시정지가 `-testmode` /
`-integration` 같은 **하네스 인자를 읽기 전에** 걸렸다.  모든 하네스의 첫 문장은
게임 시간 기준 대기(`WaitForSeconds`)라, 시간이 0배속이면 **영원히 깨어나지
않는다**.  통합·유닛·롱플레이·오토QA 10종이 실행되자마자 멈춰 있었다.

무음 실패의 전형이었다.  예외도, 실패 로그도, 붉은 글씨도 없다 — 그냥 리포트
파일이 **생성되지 않는다**.  면제 조건이 `!ReproHarness.Enabled` 라는 **특정
하네스 이름 한 줄**이었기 때문에, 유일하게 살아 있던 repro 스위트가 계속 초록불을
띄웠고 그것이 "검증은 돌고 있다"는 착시를 만들었다.  약 7주.

이걸 찾은 방법이 이 문서의 요지와 닿는다.  사람이 코드를 읽어 찾은 게 아니라,
**코드베이스 전체를 적대적으로 읽는 리뷰 에이전트**를 붙였다.  그 에이전트는
"부팅 일시정지가 하네스보다 먼저 걸린다"는 가설을 세우고, 그 가설이 참이면
반드시 있어야 할 흔적 — *리포트 JSON 이 존재하지 않을 것* — 을 파일 시스템에서
직접 확인해 왔다.  가설과 물증이 정확히 일치했다.

수정은 판정을 `Core/AutomatedRun.cs` 한 곳으로 모으는 것이다.  하네스 플래그
13종이 한 목록에 있으니, 새 하네스를 추가하는 사람이 자기 것이 왜 안 도는지
모르는 상황 자체가 사라진다.  수정 직후 통합 스위트를 실제로 돌렸다:
**51개 중 50개 통과**.  유일한 실패는 테스트가 `Btn_4x` 를 찾는데 실제 배속이
1x/3x/6x 로 바뀐, 7주 동안 아무도 못 본 드리프트였다.

> 교훈 셋.
> (a) **면제 조건을 고유명사로 적으면 안 된다.**  `!ReproHarness.Enabled` 는
>     "repro 는 예외"라고 말하지, "하네스는 예외"라고 말하지 않는다.  그 차이가
>     7주다.
> (b) **초록불의 출처를 세어 봐야 한다.**  22개가 통과하고 있었기 때문에 나머지
>     10개가 아예 실행되지 않는다는 사실이 가려졌다.  "몇 개가 통과했나"보다
>     "몇 개가 **돌았나**"가 먼저다.
> (c) 검증을 자동화한 뒤에는 **검증이 살아 있는지를 검증**해야 한다.  이 프로젝트가
>     리뷰 에이전트를 별도 역할로 두는 이유다 — 만든 쪽과 의심하는 쪽을 분리하지
>     않으면, 자기가 꺼 놓은 장치는 자기 눈에 안 보인다.

### 3.11 리뷰 지적이 틀렸고, 그걸 게이트가 잡았다

§3.10 의 리뷰 에이전트는 12건을 찾아냈고 대부분 정확했다.  하지만 하나는 틀렸다 —
그리고 그 틀린 지적을 그대로 반영했다가 회귀를 냈다.

지적은 "건축 메뉴 탭이 영문 우선(`Structure (구조)`)이라 한글 튜토리얼과 어긋난다"
였다.  소스만 보면 맞는 말이다.  그래서 8개 파일 30곳의 문자열을 `구조 (Structure)`
로 뒤집었다.  게이트를 돌리자 `p0-basics-4axis` 가 **17스텝 실패**했다.

원인: 그 문자열은 화면에 그대로 나오지 않는다.  `KrCat()` 이 **괄호 안**을 뽑아
표시하므로 탭에는 처음부터 "구조" 만 떠 있었다 — 영문은 딕셔너리 키 안에만 있었다.
순서를 뒤집자 그 함수가 이제 영문을 뽑아, 탭이 전부 영어가 되고 라벨로 버튼을 찾는
시나리오가 통째로 깨졌다.  **멀쩡한 것을 고쳐서 고장 냈다.**

> 교훈 둘.
> (a) **리뷰 결과는 가설이지 사실이 아니다.**  코드를 읽는 에이전트는 렌더된 화면을
>     보지 못한다.  "소스에 이렇게 적혀 있다"와 "화면에 이렇게 나온다"는 다른 주장이고,
>     UI 지적은 후자를 확인한 뒤에 고쳐야 한다.
> (b) **이것이 게이트를 살려 놓는 이유다.**  §3.10 에서 되살린 검증이 바로 다음
>     회차에 자기 값을 증명했다 — 7주간 꺼져 있었다면 이 회귀는 그대로 제출본에
>     들어갔을 것이다.  안전장치의 값은 잡는 순간에만 보인다.

### 3.12 "레이어가 이상하다"의 진짜 원인은 레이어가 아니었다

운영자 지적: *"침대가 벽보다 위로 올라오네 레이어가"*, *"오브젝트들 레이어 처리
제대로 되고 있나?"*

먼저 확인한 것은 정렬 체계였고, 실제로 결함이 있었다 — 이 프로젝트에는 **Y 기반
정렬이 아예 없었다.**  모든 스프라이트가 종류별 고정값(바닥 1 · 침대 4 · 벽 7 ·
주민 10)을 써서, 앞뒤 관계가 위치와 무관하게 고정돼 있었다.  그래서 주민은 벽
**뒤**에 서 있어도 항상 벽 위에 그려졌다.  발밑 y 로 정렬하는 층을 넣어 고쳤다
(기존 값은 버리지 않고 동순위 보정치로 재활용 — 손으로 맞춰 둔 상대 순서가 유지된다).

그런데 **정렬을 고쳐도 침대는 여전히 벽을 덮었다.**  여기서 추측을 멈추고 실제
경계값을 찍었다:

```
침대 스프라이트   y ∈ [-3.50, -1.50]
침대 논리 발자국  y ∈ [-3.00, -1.00]
```

반 칸이 어긋나 있었다.  원인은 정렬이 아니라 **배치**였다.  1×2 침대를 칸 중심
(`y + 0.5`)에 놓고 있었고, 2칸짜리 스프라이트는 중심 정렬이라 위아래로 반 칸씩
삐져나갔다.  건설 경로(`BuildManager`)는 이미 `y + 크기/2` 로 올바르게 계산하고
있었다 — **시작 정착지와 테스트 하네스만** 규약을 어기고 있었다.

같은 회차에 그림자도 물었다: *"모든 그림자의 방향이 적당한지 확인해봤어?"*
아침·정오·저녁 3컷을 찍어 대조하니 나무·주민·동물은 일관됐다(북서 → 짧게 북 →
북동).  가구는 처음에 "고정 그림자라 태양을 안 따라간다" 고 진단했는데, 로그를
찍어 보니 **아예 없었다** — 씬의 인스턴스 8개가 전부 `m_RemovedGameObjects`
오버라이드로 그림자 자식을 지운 상태였다.  프리팹에는 있고 씬에서만 지워져 있으니
코드를 아무리 읽어도 보이지 않는다.

> 교훈 셋.
> (a) **증상이 가리키는 층과 원인이 있는 층은 다를 수 있다.**  "레이어가 이상하다"
>     에서 정렬 결함이 실제로 나왔기 때문에, 그것만 고치고 끝냈으면 반 칸 배치
>     오류는 그대로 남았다.  고친 뒤 **다시 봐야** 한다.
> (b) **화면 문제는 화면에서 끝내지 말고 수치를 찍는다.**  픽셀을 눈대중으로 재던
>     동안은 원인 근처에도 못 갔고, 경계값 두 줄을 찍자 즉시 드러났다.
> (c) **씬/프리팹 직렬화는 코드를 조용히 이긴다.**  이 레포에서 반복된 유형이라
>     (`spawnPositions`, 동물 스탯, 이번의 그림자 자식) 이제 규칙으로 굳혔다 —
>     시각 요소는 씬 상태를 신뢰하지 말고 **없으면 코드가 만든다.**

### 3.13 세계관을 바꾸는 데 걸린 시간 — 절차 아트의 값

운영자: *"이제 먼가 특색을 주고 싶은데 머가 있을까?"*

진단은 냉정했다.  시스템(일감·니즈·연구·습격·건설)은 레퍼런스를 충실히 따라가
완성도가 나왔지만 **이 게임만 하는 것이 하나도 없어서**, 4초 봤을 때 '축소판'으로
읽혔다.  폴리싱을 아무리 더 해도 클론은 클론이다.

선택한 방향은 **한국풍 정착지**다.  시스템을 건드리지 않고 세계관만 바꾸는 것이
남은 일정에서 가장 확실한 식별 신호였고, 무엇보다 이 프로젝트의 아트가 **절차
드로잉**(코드가 직접 그림, §4)이라 리스킨이 손그림이 아니라 **코드 수정**이었다.

실제로 한 일 (같은 날 안에):
```
_gen_hanok.py         19종  심벽+기와 · 대청마루 · 창호문 · 가마솥 부뚜막 · 서안
                            소반 · 등잔 · 요/이불 · 짚자리 · 돌담 · 전돌 · 싸리울
                            사립문 · 방책 · 봉분 · 장독대 · 당산나무
_gen_hanok_flora.py    5종  소나무(적송) · 대나무 · 진달래
_gen_pawn32.py        168프레임  미색 저고리 + 깃·고름 + 색 바지 + 짚신 + 갓
```
색은 전부 `palette.py` 의 기존 램프(흙·목재·돌)에서 파생했다 — 그래서 새 에셋이
기존 지형·동물과 톤으로 갈라지지 않는다.  손으로 그렸다면 200장 가까운 스프라이트를
같은 팔레트로 유지하는 것 자체가 며칠짜리 일이다.

**바꾸지 않은 것에도 이유가 있다.**  동물(노루·멧돼지·닭·토끼·여우)은 전부 한국에
사는 종이고 작물은 이미 벼다.  바꿔야 할 이유가 없는 것을 바꾸면 이미 검증된
에셋만 흔들린다 — 리스킨의 유혹은 '전부 다시 그리기' 인데, 그건 일정이 아니라
품질을 태운다.

> 교훈 둘.
> (a) **32px 에서 '어느 나라' 를 결정하는 것은 색이 아니라 실루엣이다.**  주민을
>     흰 저고리 + 색 바지로 색만 바꿨더니 그냥 '흰 셔츠 + 색 바지' 였다.  **갓**을
>     얹은 순간 읽혔다.  나무도 같았다 — 소나무는 색이 아니라 *굽은 맨줄기 60% +
>     위쪽에만 층진 수관* 이라는 비율이 신호였다.
> (b) **절차 아트는 리스킨을 하루로 만든다.**  생성형 이미지로 200장을 뽑았다면
>     톤 드리프트를 잡느라 며칠이 갔을 것이다(§4 의 실패 사례).  코드가 그리면
>     팔레트가 단일 출처라 드리프트가 원천적으로 0 이다.

### 3.14 "안 보인다" 는 취향이 아니라 측정 가능한 값이었다

운영자: *"석재 어떤식으로 표현하는지 보고와 우리껀 너무 안보여."*

'안 보인다' 는 미적 불평처럼 들리지만, 재 보니 숫자였다.

```
ROCK_MD  밝기 0.39   ↔   GRASS_MD 밝기 0.41      (차이 0.02)
ROCK_LT  밝기 0.52   ↔   GRASS_LT 밝기 0.49      (차이 0.03)
```

돌 램프가 잔디 램프 **위에 그대로 포개져 있었다.**  색상(회색 vs 초록)이 아무리
달라도 밝기가 같으면 눈은 형태를 분리하지 못한다.  거기에 런타임이 실제로 읽는
`Resources/Sprites/prop64_stone_chunk` 는 64px @ PPU 128 = **0.5칸**이었다 —
잔디와 밝기가 같은 반 칸짜리 덩어리.  안 보이는 게 정상이었다.

레퍼런스 콜로니심의 아트 가이드를 찾아보니 규칙이 명시돼 있었다
([RWModdingResources — artstyle](https://spdskatr.github.io/RWModdingResources/artstyle.html)):
**intensity hierarchy** — 플레이어가 손댈 수 있는 것(아이템·건물)은 2~3px 검은
외곽선으로 눈에 띄고, 식물·지형은 일부러 물러난다.  우리 석재는 *주워서 나르는
물건*인데 지형처럼 그려져 있었다.  분류가 틀렸던 것이지 그림 실력의 문제가 아니었다.

고친 것: 화강암 기준 밝기 0.74(잔디와 0.25 차이) · 2px 외곽선 · 각진 파편 3개 ·
0.85칸 · 양에 따라 파편 1→3→5개.  마지막 항목은 별개 버그이기도 했다 —
석재만 단일 스프라이트로 고정돼 있어 **1개를 캐든 40개를 캐든 그림이 같았다.**

> 교훈: **"별로다" 를 받으면 먼저 재라.**  이 세션에서 세 번(레이어 → 배치,
> 그림자 방향 → 존재 여부, 작물 크기 → 임포트 PPU) 눈에 보이는 증상과 실제
> 원인의 층이 달랐다.  픽셀을 들여다보는 대신 숫자를 뽑으면 층을 건너뛰지 않는다.

### 3.15 에디터에서는 새 그림, 게임에서는 옛 그림

같은 조사 중에 더 나쁜 것이 나왔다.  스프라이트 이름이 최대 **세 곳**에 있다 —
`Sprites/`(에디터가 읽음), `Resources/Sprites/`·`Resources/struct32/`(빌드가 읽음).
생성기들이 목적지를 손으로 적고 있었고, 그래서:

| 에셋 | Sprites/ | Resources/ | 결과 |
|---|---|---|---|
| 수면자리·전돌바닥·서안·돌담 | 8/01 한국풍 | **7/26 옛 그림** | 빌드에는 서양 아트 |
| 등잔 | 8/01 한국풍 | **사본 없음** | 코드에 Resources 폴백 자체가 없어 절차 램프가 나옴 |
| 광맥 | 8/02 화강암 | 8/02 갈색 흙덩이 | 1차 수정 때 하마터면 놓칠 뻔 |

즉 **한국풍 등잔은 게임에 한 번도 들어간 적이 없었다.**  에디터 스크린샷으로는
멀쩡해 보이므로, 이 종류의 버그는 실물 빌드를 보지 않으면 영원히 안 잡힌다.

고친 방식이 요점이다.  빠진 목적지를 채워 넣는 대신 **목적지를 적지 않게** 했다
(`Assets/Sprites/_assetpaths.py`) — 같은 이름의 png 를 `Assets/` 전체에서 찾아
전부 덮고, 백업 폴더만 제외한다.  사본이 새로 생겨도 자동으로 따라온다.

> 교훈: **같은 사실이 두 곳에 적히면 언젠가 갈라진다.**  이 세션의 지배적
> 버그 유형이었다(제목 높이 62 vs 22, 작물 PPU 16 vs 32, 침대 배치 규약, 그리고
> 이번의 에셋 경로).  고칠 때 "양쪽을 맞춘다" 로 끝내면 다음에 또 갈라진다.
> **한쪽을 없애야** 끝난다.

### 3.16 같은 기능을 세 번 틀리고, 원문을 찾아 고쳤다 — 건물 그림자

운영자: *"지붕이 있는집은 그림자가 생겨야 하고"* → *"제대로 그린거 맞아? 좀
이상한거 같은데"* → *"대각선으로 생겨야할 상황에 제대로 안되는거 같은데"*.

세 번 지적받았고 세 번 다 다른 이유로 틀렸다.  기록해 둘 값어치가 있는 것은
**무엇을 틀렸나**가 아니라 **어떻게 틀린 줄 알았나**이다.

| 차수 | 구현 | 실패 | 어떻게 알았나 |
|---|---|---|---|
| 1차 | 지붕 다각형을 태양 반대로 이동 | 건물에서 떨어진 네모가 풀밭에 놓임 | 4시각 스크린샷 — 08시에만 보이고 11/14/17시 사라짐 |
| 2차 | 밑동 테두리(접지선) | '서 있다'는 되고 '드리웠다'는 안 됨 | 휘도 측정 — 네 시각 모두 −7~14 (너무 약함) |
| 3차 | 벽 외곽선을 태양 반대로 쓸기 | 대각선이 수평으로 뭉개짐 | 나무 그림자와 나란히 비교 — 나무만 대각선 |

1차의 진짜 원인은 로그 한 줄이 알려줬다:

```
[RoofShadow] 지붕칸=21 그림자=9장 길이=2.54칸
```

지붕 다각형은 **건물 발자국과 같다.**  그래서 밀어낸 칸이 대부분 건물 자신 위에
떨어져 걸러지고, 남는 건 벽 뒤에 가리는 조각뿐이었다.  "그림자가 없다"가 아니라
"그림자가 9장 있는데 안 보인다"였고, 그 구분은 눈으로는 불가능했다.

방향이 잡힌 것은 **레퍼런스의 개발자 원문**을 찾은 뒤였다:

> "shadows from the sun that fade in and out based on **time of day**, **move
> across the ground**, **don't shade indoors**, come from people and small
> objects as well as **large structures**, project to **varying heights**, and
> change color slightly to **complement the color of the sky**"

여기서 읽어야 할 것은 **그림자를 던지는 주체가 지붕이 아니라 물체**라는 점이다.
지붕은 오히려 '그림자를 받지 않는 곳'으로만 쓰인다.  구조가 처음부터 틀렸던 것이지
숫자가 틀린 게 아니었다.

3차의 대각선 실종도 측정이 잡았다.  세로 성분에 0.55를 곱하고 있었는데(나무
셰이더의 전단 계수를 그대로 가져왔다 — 성격이 다른 값이다), 정수 칸으로 반올림하니
`0.11 / 0.23 / 0.34` 가 **전부 0** 이 됐다.  어느 시각에도 수평 띠만 나온 이유다.

> 교훈: **레퍼런스를 '따라 만든다'와 '원문을 읽는다'는 다르다.**  세 번의 실패는
> 전부 레퍼런스를 *본떠* 만든 결과였고, 개발자가 직접 쓴 한 문장이 구조를 바로잡았다.
> 그리고 **보이지 않는 것을 디버깅하려면 화면이 아니라 로그를 봐야 한다** — 이
> 기능은 "9장 그렸다"는 한 줄이 나오기 전까지 원인 근처에도 못 갔다.

### 3.17 '재미없다'를 숫자로 바꾸기

운영자: *"유저의 재미를 점수화 시켜서 재미에 대한 점수를 올려야 할 거 같아."*

이 제안이 나온 배경이 기록에 남아 있다.  **같은 문제를 사흘에 걸쳐 세 번 다른
말로 진단하고 있었다:**

| 날짜 | 운영자 표현 | 실제로 같은 것 |
|---|---|---|
| 07-30 | "영상 100점 만점에 2점" | 사건이 없다 |
| 07-31 | "뭐 하고 있는건지 모르겠음" | 활력이 없다 |
| 08-02 | "10분간 숫자가 안 움직인다" | 진행감이 없다 |

톤·에셋 드리프트는 이미 수치로 판정하고 있었는데(`check-art-tone.py`,
`check-asset-drift.py`) **재미만 감상으로 남아 있었다.**  그래서 고칠 때마다 다른
축을 건드리고, 올랐는지도 알 수 없었다.

도입한 구조:

```
FunTelemetry.cs        5초마다 상태를 JSONL 로 (-funscore 인자 있을 때만)
scripts/fun-score.py   100점 루브릭 → 축별 점수 + "가장 크게 잃는 축"
docs/fun-rubric.md     기준·근거·점수 이력
```

루브릭은 **심사자의 10분**을 본다 (게임잼 심사 통설: 엔트리당 5~15분).
30시간 뒤에 재미있는 것은 0점이다 — 심사자가 볼 수 없기 때문이다.

첫 측정 (10.6분, 표본 128개):

```
재미 점수  46.7 / 100
  진행감   16.5/30   목표 +2 / 구조물 +0 / 가치 x2.66
  사건      7.2/25   3건 (0.3/분), 최장 침묵 475초
  활력     13.0/20   유휴 34%, 동시 활동 1.3종
  긴장      0.0/15   위협 발생 0 / 해소 0
  다양성   10.0/10   활동 14가지
```

설계에서 의도적으로 가른 두 가지가 있다.

**① 사건은 훅이 아니라 상태 변화에서 유도한다.**  시스템마다 콜백을 박으면 훅이
늘 때마다 계측이 갈라진다.  목표 수·구조물 수·연구 수·적 수의 증감을 보고 사건을
읽으므로, 계측 대상이 늘어도 파일 하나만 본다.

**② 루브릭은 게임 밖에 둔다.**  루브릭은 자주 바뀌는데 게임은 자주 빌드할 수 없다.
게임은 **사실만** 남기고 해석은 밖에서 한다 — 덕분에 과거 세션의 JSONL 을 새
루브릭으로 다시 채점할 수도 있다.

> 교훈: **"재미없다"는 감상이 아니라 미측정 상태다.**  축을 정하고 목표선을 적는
> 순간 "무엇을 고쳐야 몇 점 오르는가"로 바뀐다.  이 루브릭이 만점이어도 재미없을
> 수 있다 — 다만 **낮으면 확실히 재미없다.**  그 하한을 막는 도구다.

## 4. 아트 파이프라인 — 생성형을 어디에 쓰고 어디에 안 쓰는가

생성형 단독 아트는 **장간 스타일 드리프트로 한 번 실패했다** (연쇄 반려).
그래서 노선을 나눴다.

| 대상 | 방법 | 이유 |
|---|---|---|
| 지형·자원·유닛 | 외부 에셋 팩 | 톤의 기준점.  일관성이 이미 보장됨 |
| 가구·구조물·아이콘 | **절차 드로잉** (코드가 직접 그림) | 드리프트 0.  팩 팔레트·아웃라인 규약을 코드로 강제 |
| 유기물 (나무 등) | **팩 스타일 LoRA 정합 생성** | 팩에 없는 종류를 팩 톤으로 |

생성 파이프라인(`gen-trees-lora.py`)의 실제 지시:

```
트리거:  "tswords style game sprite, a <종 묘사>, top-down three-quarter view,
          centered on plain flat solid violet purple background, no shadow,
          no gradient, isolated object"
LoRA:    tswords_v1.safetensors  (팩 스타일 자체 훈련)
후처리:  모서리 시드 flood fill 키잉 → 크롭·축소 → 채도 정렬 → 팔레트 양자화
          → 팩 아웃라인 확정
게이트:  check-art-tone.py 통과해야 반입
```

**배경색이 청보라인 이유**도 기록해 둔다.  1차에는 마젠타를 썼는데 단풍 빨강과
색상각이 30° 밖에 안 떨어져, 잔상 제거 임계를 조금만 올려도 단풍 잎이 같이
파였다(실측: tol80 에서 27.6% 손실).  청보라는 이 게임의 나무 색 전체와 82° 이상
떨어진다.  **키잉은 반드시 연결성 기반**(flood fill)이어야 하며 단순 색거리
임계는 쓰지 않는다.

## 6. 이 문서가 본선과 어떻게 이어지는가

본선 산출물은 게임 프로토타입 + **에이전트 설계서** + **디렉팅 명세서**다.
위 §2 가 에이전트 설계서, §3~4 가 디렉팅 명세서의 실물이다 —
지금 돌아가고 있는 것을 기술한 것이지, 본선용으로 새로 쓴 것이 아니다.
