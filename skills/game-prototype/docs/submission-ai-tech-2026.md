## 1. 두 층은 같은 구조다

> **한 줄로**  플레이어가 주민에게 명령하지 않듯, 제작자도 AI 에게 코드를 받아쓰게
> 하지 않는다.  둘 다 *무엇을* 만 정하고 *어떻게* 는 상대가 정한다.


PawnSim 은 조선 산골 마을을 키우는 간접 조작 시뮬레이션이다.  플레이어는 유닛을
직접 조종하지 않는다 — **일감을 지정**하면, 주민이 각자의 작업 우선순위와 숙련도,
그리고 지금 배고픈지 졸린지 같은 상태를 따져 무엇을 언제 할지 스스로 정한다.

이 게임은 **같은 방식으로 만들어졌다.**  제작자는 코드를 직접 쓰지 않는다 —
방향을 지정하면 역할별 에이전트가 각자의 정책으로 판단해 만든다.

```
┌─ 게임 안 ─────────────────────────────┐   ┌─ 게임 밖 ─────────────────────────────┐
│ 플레이어                              │   │ 제작자(디렉터)                        │
│   ↓ "무엇을"만 지정                   │   │   ↓ "무엇을"만 지정                   │
│ 작업 우선순위 그리드 (6인 × 9직종)    │   │ 정책 (config/policies.yaml)           │
│   · 0=비활성 1~4=우선순위             │   │   · 자율 범위 / 유료 결제는 승인 필요 │
│   · 숙련도에서 기본값 유도            │   │   · 로직 변경은 승인 필요             │
│   ↓                                   │   │   ↓                                   │
│ PawnUtilityAI                         │   │ 역할 에이전트                         │
│   · 후보 행동 8종을 점수로 비교       │   │   · planner / artist / programmer     │
│   · 상태·기분·일과가 선택에 개입      │   │   · qa / ta / auditor                 │
│   ↓                                   │   │   ↓                                   │
│ "누가 언제 어떻게"는 에이전트가 결정  │   │ "누가 언제 어떻게"는 에이전트가 결정  │
└───────────────────────────────────────┘   └───────────────────────────────────────┘
```

게임 안과 밖이 **같은 문장으로 설명된다** — 이것이 이 제출물이 말하려는 것이다.

## 2. 제작 구조 — 무엇이 무엇을 판단하는가

> **한 줄로**  만드는 쪽과 판정하는 쪽을 사람이 아니라 **역할로 분리**했다.
> 판정은 눈이 아니라 게이트가 하고, 게이트는 자기 임계까지 검증한다.


### 2.1 역할 분리

에이전트 정의는 `.claude/agents/*.md` 에 있고, 각각 도구 권한과 판단 범위가 다르다.
게임 제작에 실제로 쓰인 것:

| 에이전트 | 판단하는 것 | 도구 |
|---|---|---|
| `game-designer` | 시스템·메카닉·조작 | 읽기/쓰기 |
| `game-programmer` | 스크립트 구현 | 읽기/쓰기/편집/실행 |
| `game-build-engineer` | 씬 조립과 빌드 자동화 | 읽기/쓰기/편집/실행 |
| `game-qa` | 빌드 실행 → 스크린샷 → 판정 | 읽기/실행 |
| `ta` | **아트 자산의 미적 품질 채점** (제작자와 분리된 눈) | 읽기/실행 |
| `auditor` | 저장소 전반의 드리프트 감사 (읽기 전용) | 읽기/실행 |

핵심은 `ta` 와 `auditor` 다.  **만드는 주체와 판정하는 주체를 분리**해야 "만든
사람이 자기 결과물을 좋게 보는" 편향이 끊긴다.

### 2.2 판정은 사람의 눈이 아니라 게이트가 한다

지각적 주장("톤이 이상하다")은 재현되지 않는다.  그래서 **수치로 바꿔 게이트에
넣는다.**  현재 가동 중인 것:

| 게이트 | 무엇을 잡나 |
|---|---|
| `check-art-tone.py` | 팩 톤 서명 이탈 — 외곽선 휘도·색 수·채도·명도 |
| `check-asset-refs.py` | 끊긴 스프라이트 참조 (조용히 안 그려짐) |
| `check-sprite-ppu.py` | 등록 PPU ≠ `.meta` (엉뚱한 크기로 들어감) |
| `check-font-coverage.py` | 폰트에 없는 문자 (빈칸으로 그려짐) |
| `spec-sync.py` | 기획서 ↔ 구현 드리프트 (유령 컴포넌트·그림자 상수·문서 수치) |
| `repro_all.py` | 재현 시나리오 24종 (기능 회귀) — 측정 전용 `_` 접두 22종은 게이트 제외 |
| `UiSweepQA` | **모든 버튼을 눌러 보고 반응 없는 것** |

넷은 공통점이 있다 — **빌드는 성공하는데 화면만 잘못되는** 종류를 잡는다.
컴파일·테스트가 구조적으로 못 보는 사각지대다.

### 2.3 게이트는 자기 임계를 검증한다

임계값을 사람이 감으로 정하면 그 게이트는 신뢰할 수 없다.  그래서 각 게이트는
`--self-test` 로 **기준선이 자기 임계를 통과하는지** 확인한다.

- `check-art-tone --self-test` → 팩 원본 12종이 전부 PASS 해야 한다 (12/12)
- `spec-sync --self-test` → 알려진 사고 4종을 재현해 탐지기가 실제로 잡는지 확인

한 번도 빨간불을 본 적 없는 게이트는 게이트가 아니다.

## 3. AI 대상 주요 프롬프트 및 지시 사항

> **한 줄로**  지시는 대화창에 그때그때 적는 것이 아니라 **저장소에 커밋된 파일**
> 네 층이다.  그래서 세션이 바뀌어도 같은 판단이 나온다.


이 시스템에서 AI 에게 주는 지시는 **네 층**으로 나뉘고, 각각 파일로 저장돼 있다.
대화창에 그때그때 적는 즉흥 프롬프트가 아니라 **저장소에 커밋된 규칙**이라, 세션이
바뀌어도 같은 판단이 재현된다.  아래는 실제 파일에서 그대로 옮긴 것이다.

| 층 | 파일 | 무엇을 지시하나 |
|---|---|---|
| 1 | `CLAUDE.md` | 세션 시작 절차, 작업 방식, 커밋 규칙 |
| 2 | `docs/operator-contract.md` | 하드 룰 13개 (돈·로직 변경·중단 금지 등) |
| 3 | `config/policies.yaml` | 자율 범위 — 무엇을 물어보고 무엇을 그냥 하나 |
| 4 | `.claude/agents/*.md` | 역할별 시스템 프롬프트 |

### 3.1 1층 — 세션이 시작될 때 가장 먼저 읽는 것

```
모든 대화는 두 파일을 순서대로 읽는다.
1. docs/goal.md — 결과 층.  "무엇이 완성이면 성공인가."
   할 일 목록이 비었다고 목표가 달성된 것이 아니다.
2. docs/roadmap.md — 작업 큐.  "오늘 무엇부터."
```

> 이 순서는 사고에서 나왔다.  이틀 동안 인프라 커밋 11개가 쌓이고 작업 큐는 0건
> 이었는데, **정작 만들어야 할 결과물은 0개**였다.  큐가 비었다는 신호를 완료로
> 읽은 것이다.  그래서 결과 층과 작업 층을 분리하고, 결과 층을 먼저 읽게 했다.

작업 방식 지시도 같은 파일에 있다 — 이 프로젝트에서 가장 자주 인용되는 문장들이다.

```
- 작업 중간에 확인 질문으로 멈추지 말 것.  판단이 갈리는 지점은 합리적인
  기본값을 스스로 정하고 계속 진행한 뒤, 어떤 가정을 했는지 최종 보고에 정리할 것.
- 계획만 세우고 멈추지 말 것.  계획을 세웠으면 승인을 기다리지 말고 바로 실행할 것.
- 오류가 나면 보고하고 멈추지 말고, 원인을 찾아 수정한 뒤 계속 진행할 것.
- 작업이 끝나면 테스트나 빌드로 스스로 검증한 뒤 결과를 보고할 것.
```

### 3.2 2층 — 절대 어기면 안 되는 것

`operator-contract.md` 의 하드 룰 중 게임 제작에 실제로 작동한 넷:

```
§1  에이전트가 모든 작업을 한다 — 사용자는 터미널을 만지지 않는다.
    설치·편집·설정·커밋·푸시 전부 에이전트가 한다.
§3  돈 방화벽 — 유료 API·SaaS·클라우드 자원 생성은 반드시 사용자 확인.
    로컬 자원(ffmpeg, ollama, whisper)은 확인 없이 사용.
§4  로직 변경은 명시적 승인 — agents/*.md 편집은 자율 모드와 무관하게 정지.
§5  지시 없이는 멈추지 않는다 — 사용자는 비동기다.  "아니면 잠깐 멈출까요?" 는
    몇 시간의 공회전이 된다.
```

§4 가 이 시스템의 안전핀이다.  **에이전트가 자기 정의를 스스로 고칠 수 없다.**
품질 게이트를 통과하지 못할 때 게이트를 낮추는 대신 결과물을 고치게 하는 것도
같은 원리다.

### 3.3 3층 — 자율 범위

`config/policies.yaml` 은 "물어볼 것"과 "그냥 할 것"을 갈라 놓는다.

```yaml
mode:
  default: interactive          # interactive | autonomous
  switch_via: AUTONOMY_MODE

interactive:
  pause_for:
    - logic_change              # agents/*.md 편집
    - destructive_fs            # rm -rf, 디스크 초기화
    - external_publish          # 업로드·배포
    - paid_api                  # 유료 호출

autonomous:
  budget_usd: <상한>            # 초과 시 중단 로그를 남기고 정지
  never:
    - agent_definition_edit     # 무인 상태에서는 절대
```

### 3.4 4층 — 역할별 시스템 프롬프트

에이전트마다 **판단 기준과 도구 권한이 다르다.**  아래는 아트 품질을 채점하는
`ta`(테크니컬 아티스트)의 프롬프트 앞부분 — 실제 파일 그대로다.

```
너는 이 프로젝트의 **테크니컬 아티스트(TA)** 다.  역할은 둘:

1. 아트 디렉션 수호자 — 정본 art-style-guide-v3.md 의 집행자.
   규정: 채도 3단(지형≤0.45 / 오브젝트≤0.65 / 캐릭터≤0.75),
   밸류 3계급(지형 어두움 < 오브젝트 < 캐릭터·포커스),
   무광(글로시 금지), 좌상광, 계절 고정,
   아웃라인은 인터랙티브 오브젝트만.

2. 디자인 QA — 제작 과정을 모르는 신선한 눈으로 채점.
```

마지막 문장이 핵심이다 — **"제작 과정을 모르는 신선한 눈"**.  만든 주체가 자기
결과물을 채점하면 "이만하면 됐다"가 나온다.  그래서 `ta` 와 `auditor` 는 쓰기
권한이 아예 없고(`Read, Glob, Grep, Bash`), 판정과 수정 지시만 낸다.

### 3.5 지시가 실제로 작동한 증거

프롬프트를 적어두는 것과 그 프롬프트가 결과를 바꾸는 것은 다르다.  아래 §4 의
사례들이 그 차이를 보여준다 — 전부 **지시가 없었으면 그냥 넘어갔을** 것들이다.

| 지시 | 그 지시가 잡아낸 것 |
|---|---|
| "빌드로 스스로 검증한 뒤 보고" | 배포본이 9커밋 뒤처져 있던 것 |
| "제작 과정을 모르는 눈으로 채점" | 주민 여섯이 전부 똑같아 보이던 것 |
| "게이트를 낮추지 말고 결과물을 고쳐라" | 테스트 임계 완화 대신 원인 수정 |
| "결과 층을 먼저 읽어라" | 큐가 비었는데 결과물이 0개이던 상태 |

![같은 장면을 아침·정오·저녁에 찍은 것. 그림자가 해를 따라 방향과 길이를 바꾼다. 이런 종류는 **빌드가 성공하고 테스트도 통과하는데 화면만 틀린다** — 컴파일러가 볼 수 없는 사각지대라, 재현 시나리오가 시각을 강제로 옮겨 가며 스크린샷을 남기고 판정한다.](figures/05-shadow-times.png)

## 4. 증거 — 지시가 실제로 잡아낸 것

> **이 절을 읽는 법**  아래 표가 전부다.  세 사례만 자세히 적고 나머지는 줄였다 —
> 열아홉 개를 다 읽히려는 문서는 하나도 안 읽힌다.  전체 기록은 저장소
> `skills/game-prototype/docs/` 에 날짜별로 남아 있다.

**왜 이 절이 필요한가.**  "AI 에게 이렇게 지시했다"는 말은 누구나 할 수 있다.
그 지시가 **결과를 바꿨다는 증거**가 있어야 기술 문서다.  아래는 전부 지시가
없었으면 그냥 넘어갔을 것들이고, 각각 커밋과 스크린샷이 남아 있다.

| # | 무엇이 잘못돼 있었나 | 무엇이 그것을 잡았나 |
|---|---|---|
| 1 | 새 아트가 팩 톤에서 벗어났는데 사람 눈은 통과시켰다 | 톤 게이트(수치 판정) |

### 3.10 안전장치가 7주간 꺼져 있었고, 그걸 찾은 것도 에이전트였다

§3.8 은 게이트 하나가 조용히 꺼져 있던 이야기다.  더 큰 것이 뒤에 있었다.

게임은 **일시정지 상태로 부팅**한다 — 플레이어가 맵을 둘러보고 계획한 뒤 직접
시작하는 편이 이 장르에 맞기 때문이다.  그런데 이 일시정지가 `-testmode` /
`-integration` 같은 **하네스 인자를 읽기 전에** 걸렸다.  모든 하네스의 첫 문장은
게임 시간 기준 대기(`WaitForSeconds`)라, 시간이 0배속이면 **영원히 깨어나지
않는다**.  통합·유닛·롱플레이·오토QA 10종이 실행되자마자 멈춰 있었다.

무음 실패의 전형이었다.  예외도, 실패 로그도, 붉은 글씨도 없다 — 그냥 리포트
파일이 **생성되지 않는다**.  면제 조건이 `!ReproHarness.Enabled` 라는 **특정
하네스 이름 한 줄**이었기 때문에, 유일하게 살아 있던 재현 시나리오 묶음이 계속 초록불을
띄웠고 그것이 "검증은 돌고 있다"는 착시를 만들었다.  약 7주.

이걸 찾은 방법이 이 문서의 요지와 닿는다.  사람이 코드를 읽어 찾은 게 아니라,
**코드베이스 전체를 적대적으로 읽는 리뷰 에이전트**를 붙였다.  그 에이전트는
"부팅 일시정지가 하네스보다 먼저 걸린다"는 가설을 세우고, 그 가설이 참이면
반드시 있어야 할 흔적 — *리포트 JSON 이 존재하지 않을 것* — 을 파일 시스템에서
직접 확인해 왔다.  가설과 물증이 정확히 일치했다.

수정은 판정을 `Core/AutomatedRun.cs` 한 곳으로 모으는 것이다.  하네스 플래그
13종이 한 목록에 있으니, 새 하네스를 추가하는 사람이 자기 것이 왜 안 도는지
모르는 상황 자체가 사라진다.  수정 직후 전체 검증을 실제로 돌렸다:
**51개 중 50개 통과**.  유일한 실패는 테스트가 `Btn_4x` 를 찾는데 실제 배속이
1x/3x/6x 로 바뀐, 7주 동안 아무도 못 본 드리프트였다.

> 교훈 셋.
> (a) **면제 조건을 고유명사로 적으면 안 된다.**  `!ReproHarness.Enabled` 는
>     "repro 는 예외"라고 말하지, "하네스는 예외"라고 말하지 않는다.  그 차이가
>     7주다.
> (b) **초록불의 출처를 세어 봐야 한다.**  22개가 통과하고 있었기 때문에 나머지
>     10개가 아예 실행되지 않는다는 사실이 가려졌다.  "몇 개가 통과했나"보다
>     "몇 개가 **돌았나**"가 먼저다.
> (c) 검증을 자동화한 뒤에는 **검증이 살아 있는지를 검증**해야 한다.  이 프로젝트가
>     리뷰 에이전트를 별도 역할로 두는 이유다 — 만든 쪽과 의심하는 쪽을 분리하지
>     않으면, 자기가 꺼 놓은 장치는 자기 눈에 안 보인다.

### 3.17 '재미없다'를 숫자로 바꾸기

운영자: *"유저의 재미를 점수화 시켜서 재미에 대한 점수를 올려야 할 거 같아."*

이 제안이 나온 배경이 기록에 남아 있다.  **같은 문제를 사흘에 걸쳐 세 번 다른
말로 진단하고 있었다:**

| 날짜 | 운영자 표현 | 실제로 같은 것 |
|---|---|---|
| 07-30 | "영상 100점 만점에 2점" | 사건이 없다 |
| 07-31 | "뭐 하고 있는건지 모르겠음" | 활력이 없다 |
| 08-02 | "10분간 숫자가 안 움직인다" | 진행감이 없다 |

톤·에셋 드리프트는 이미 수치로 판정하고 있었는데(`check-art-tone.py`,
`check-asset-drift.py`) **재미만 감상으로 남아 있었다.**  그래서 고칠 때마다 다른
축을 건드리고, 올랐는지도 알 수 없었다.

도입한 구조:

```
FunTelemetry.cs        5초마다 상태를 JSONL 로 (-funscore 인자 있을 때만)
scripts/fun-score.py   100점 루브릭 → 축별 점수 + "가장 크게 잃는 축"
docs/fun-rubric.md     기준·근거·점수 이력
```

루브릭은 **심사자의 10분**을 본다 (게임잼 심사 통설: 엔트리당 5~15분).
30시간 뒤에 재미있는 것은 0점이다 — 심사자가 볼 수 없기 때문이다.

첫 측정 (10.6분, 표본 128개):

```
재미 점수  46.7 / 100
  진행감   16.5/30   목표 +2 / 구조물 +0 / 가치 x2.66
  사건      7.2/25   3건 (0.3/분), 최장 침묵 475초
  활력     13.0/20   유휴 34%, 동시 활동 1.3종
  긴장      0.0/15   위협 발생 0 / 해소 0
  다양성   10.0/10   활동 14가지
```

설계에서 의도적으로 가른 두 가지가 있다.

**① 사건은 훅이 아니라 상태 변화에서 유도한다.**  시스템마다 콜백을 박으면 훅이
늘 때마다 계측이 갈라진다.  목표 수·구조물 수·연구 수·적 수의 증감을 보고 사건을
읽으므로, 계측 대상이 늘어도 파일 하나만 본다.

**② 루브릭은 게임 밖에 둔다.**  루브릭은 자주 바뀌는데 게임은 자주 빌드할 수 없다.
게임은 **사실만** 남기고 해석은 밖에서 한다 — 덕분에 과거 세션의 JSONL 을 새
루브릭으로 다시 채점할 수도 있다.

> 교훈: **"재미없다"는 감상이 아니라 미측정 상태다.**  축을 정하고 목표선을 적는
> 순간 "무엇을 고쳐야 몇 점 오르는가"로 바뀐다.  이 루브릭이 만점이어도 재미없을
> 수 있다 — 다만 **낮으면 확실히 재미없다.**  그 하한을 막는 도구다.

### 3.18 코드를 고쳤는데 아무 일도 안 일어났다 — 씬이 이기고 있었다

§3.17 의 루브릭을 만들자마자 그 값을 올리러 갔다.  '긴장' 축이 0/15 였고 원인은
명확해 보였다 — 첫 습격이 심사창 밖(실제 16~27분)에 잡힌다.  `RaidGraceDays`
기본값을 2 → 1 로 고치고 다시 쟀다.

**여전히 0/15.**  습격 0건.

두 번째로 고쳤다.  첫 습격 전용 대기(`FirstRaidWaitDays = 0.8`)를 새로 넣었다.
**또 0/15.**

세 번째에야 코드가 아니라 데이터를 봤다:

```
Assets/Scenes/Game.unity
  RaidGraceDays: 2      ← 씬에 직렬화된 값
```

`[SerializeField]` 필드는 씬에 값이 저장돼 있으면 **코드의 초기값이 무시된다.**
그런데 실패가 조용하다 — 컴파일도 되고, 게이트 24/24 도 통과하고, 그냥 아무 일이
일어나지 않는다.  코드를 읽으면 `= 1` 이라고 쓰여 있으니 **사람 눈으로는 영원히
안 보인다.**

이 레포가 같은 함정을 밟은 것이 이번이 처음이 아니다:

| 언제 | 무엇이 씬에 굳어 있었나 | 증상 |
|---|---|---|
| 이전 | 스폰 좌표 · 동물 스탯 · 광맥 스탯 · 수종 | 코드 수정이 화면에 안 나타남 |
| 이전 | 가구 그림자 자식 (`m_RemovedGameObjects`) | "그림자 방향이 이상하다" → **실은 없었다** |
| 이번 | `RaidGraceDays` | 습격이 영원히 안 옴 |

그래서 값을 고치는 데서 멈추지 않고 **검사를 만들었다** —
`scripts/check-scene-overrides.py` 는 `[SerializeField]` 필드의 코드 기본값을
파싱해 씬 YAML 의 같은 이름 값과 비교하고, 다른 것을 전부 보고한다.
첫 실행에서 **39건**이 나왔다 (대부분은 의도적 튜닝 — 동물 개체별 이동속도 등).

중요한 것은 판정이 아니라 **가시성**이다.  이 검사가 말하는 것은 "이 값은
틀렸다" 가 아니라 **"이 값은 코드를 고쳐도 안 바뀐다"** 이고, 판단은 사람이 한다.

> 교훈: **같은 증상을 세 번 보면 층을 바꿔라.**  두 번은 코드를 고쳤고 두 번 다
> 실패했다.  세 번째에 "코드가 실행되고는 있나"를 물었어야 했다.
> 그리고 **조용한 실패는 반드시 검사로 바꿔야 한다** — 컴파일도 되고 테스트도
> 통과하는데 아무 일이 안 일어나는 종류는, 다음에도 똑같이 못 잡는다.


> **나머지 열여섯**은 같은 형태다 — 무언가 잘못돼 있었고, 사람 눈이 아니라
> 게이트나 분리된 판정자가 그것을 잡았고, 고친 뒤 그 사고를 **재현 시나리오로
> 박아** 다시는 돌아오지 못하게 했다.  현재 게이트는 24종이 매 커밋 돈다.

## 5. 아트 파이프라인 — 생성형을 어디에 쓰고 어디에 안 쓰는가

> **한 줄로**  생성형은 '한 장을 잘 뽑는' 데는 강하지만 **여러 장의 톤을 맞추는**
> 데는 약하다.  그래서 기준점은 팩과 절차 생성이 잡고, 생성형은 그 안에서만 쓴다.


생성형 단독 아트는 **장간 스타일 드리프트로 한 번 실패했다** (연쇄 반려).
그래서 노선을 나눴다.

| 대상 | 방법 | 이유 |
|---|---|---|
| 지형·자원·유닛 | 외부 에셋 팩 | 톤의 기준점.  일관성이 이미 보장됨 |
| 가구·구조물·아이콘 | **절차 드로잉** (코드가 직접 그림) | 드리프트 0.  팩 팔레트·아웃라인 규약을 코드로 강제 |
| 유기물 (나무 등) | **팩 스타일 LoRA 정합 생성** | 팩에 없는 종류를 팩 톤으로 |

생성 파이프라인(`gen-trees-lora.py`)의 실제 지시:

```
트리거:  "tswords style game sprite, a <종 묘사>, top-down three-quarter view,
          centered on plain flat solid violet purple background, no shadow,
          no gradient, isolated object"
LoRA:    tswords_v1.safetensors  (팩 스타일 자체 훈련)
후처리:  모서리 시드 flood fill 키잉 → 크롭·축소 → 채도 정렬 → 팔레트 양자화
          → 팩 아웃라인 확정
게이트:  check-art-tone.py 통과해야 반입
```

**배경색이 청보라인 이유**도 기록해 둔다.  1차에는 마젠타를 썼는데 단풍 빨강과
색상각이 30° 밖에 안 떨어져, 잔상 제거 임계를 조금만 올려도 단풍 잎이 같이
파였다(실측: tol80 에서 27.6% 손실).  청보라는 이 게임의 나무 색 전체와 82° 이상
떨어진다.  **키잉은 반드시 연결성 기반**(flood fill)이어야 하며 단순 색거리
임계는 쓰지 않는다.

절차 생성기는 저장소에 **34개** 커밋돼 있다 (`Assets/Sprites/_gen_*.py`).
색은 전부 `palette.py` 의 기준 램프에서 파생되므로, 생성기를 다시 돌리면 **같은
그림이 재현된다** — 이미지 파일이 아니라 **그리는 코드**가 산출물이라는 뜻이다.

**재배포 금지 준수 설계**: 팩 추출물은 저장소에 커밋하지 않고, 팩이 없는 클린
클론에서도 게임이 정상 빌드되도록 **절차 생성 폴백 경로**를 갖췄다
(지형 16조각 + 자체 생성 수종 5종).  라이선스를 지키면서 재현 가능성을 잃지
않기 위한 구조다.

## 7. 이 문서가 본선과 어떻게 이어지는가

> **한 줄로**  본선은 주제를 모른 채 48시간이다.  그때 필요한 것은 완성된 게임이
> 아니라 **무엇이 와도 돌아가는 제작 구조**다.


본선 산출물은 게임 프로토타입 + **에이전트 설계서** + **디렉팅 명세서**다.
위 §2 가 에이전트 설계서, §3~4 가 디렉팅 명세서의 실물이다 —
지금 돌아가고 있는 것을 기술한 것이지, 본선용으로 새로 쓴 것이 아니다.

### 48시간에 실제로 남는 것

본선은 **주제를 모른 채** 시작한다.  그러니 미리 만들어 갈 수 있는 것은 게임이
아니라 **게임을 만드는 방법**이다.  아래는 주제가 무엇으로 정해지든 첫 시간부터
그대로 쓰는 것들이고, 전부 이미 돌아가고 있다.

| 가져가는 것 | 주제가 바뀌어도 쓰는 이유 |
|---|---|
| 역할 에이전트 6종 | 기획·구현·아트·검증의 분업은 장르와 무관하다 |
| 재현 시나리오 하네스 | 게임을 자동 조작해 결과를 검사 — 무슨 게임이든 클릭은 한다 |
| 게이트 24종 중 아트·자산 계열 | 톤 이탈·끊긴 참조·PPU 불일치는 어느 프로젝트에나 생긴다 |
| 재미 점수 루브릭 | "재미없다"를 고칠 수 있는 형태로 바꾸는 절차 |
| 촬영·문서 파이프라인 | 마지막 날 밤에 영상·PDF 를 만들다 망하는 일이 없다 |

### 이 사전과제에서 실제로 걸린 시간

| 일 | 걸린 시간 |
|---|---|
| 세계관 전환 (판타지 → 조선 산골) | 절차 아트라 **하루** — 자산을 다시 그리지 않았다 |
| "재미없다" → 수치화 → 46.7 → 78.1 | 하루 |
| 시연 영상 전면 재제작 (촬영 방법 자체를 새로 세움) | 하루 |

세 가지 모두 **사람이 손으로 그리거나 편집한 것이 아니다.**  구조가 있으면
방향 전환의 비용이 이만큼 내려간다는 것이, 48시간짜리 대회에서 이 시스템이
갖는 의미다.
