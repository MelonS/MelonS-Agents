# 읽히지 않는 콜로니 — 진행과 의미 (2026-07-31)

운영자 판정: *"현재 버전에 높은 점수 못주겠음. 탈락수준임"*, *"내가 심사위원이면 이건 절대
못올라감"*, 그리고 결정적으로 *"플레이 영상을 보고 있으면 동작 하나하나에 의미가 있어야
하는데 머하고 있는건지 모르겠음."*

전제도 한 번 바로잡았다.  대회 문구("AI의 다음 단계를 설계할 디렉터")를 *게임 안에 AI를
넣으라*로 읽고 런타임 LLM 서사 계층을 설계하려 했는데, 운영자 교정: **AI로 게임을 만들 때
남들이 못 하는 수준을 내는 사람**을 찾는다는 뜻이다.  AI는 제작 과정에 있는 것이지 제품
안에 있어야 하는 게 아니다.  그리고 본선 기준은 *"사람이 만든 것과 비교가 힘든 수준"*.
→ 할 일은 새 기능이 아니라 **게임 자체의 질**이다.

## 1. 진단 방법 — 추측 대신 스틸을 시간순으로 읽었다

제출용 데모 스틸 6장(`art-out/demo/shots/d00..d05`)을 **시각 순서대로** 놓고 숫자만 비교했다.

| | d00 (6:05 AM) | d05 (10:15 AM) | 판정 |
|---|---|---|---|
| 정착 목표 | 1/4 | **1/4** | 4게임시간 동안 진행 0 |
| 목재 | 200 | 350 | 쌓이기만 — 아무것도 안 지어짐 |
| 연구 | 0/100 | **7/100** | 하루 7% → 영원히 미완 |
| 튜토리얼 | ① 일감 지정 | **③ 농장 (고정)** | 화면 중앙을 내내 가림 |

이 표가 이후 작업의 전부를 결정했다.  "느낌이 밋밋하다"가 아니라 **화면에 찍힌 숫자가
움직이지 않는다**는 사실에서 출발해야 원인까지 갈 수 있다.

## 2. 근본 원인 6가지 — 전부 "코드는 있는데 안 닿는" 유형

### ① 목표 1번이 첫 프레임부터 이미 달성돼 있었다
`WoodGoal = 200` 인데 시작 저장구역 적립분이 200 이다.  체크리스트가 1/4 로 열리고,
나머지 셋은 아래 이유로 도달 불가 → **4분 내내 1/4 고정**.
→ `WoodGoal = 400`.  시작 화면이 200/400 = 절반 찬 상태로 열려 카운터가 살아 있다는 것도
같이 읽힌다.

### ② 시작 집에 문이 없었다 → 지붕이 안 생겼다 → "지붕 아래 잠자리 0/3"
`SceneSetup` 이 문간 칸에서 벽 생성을 `continue` 로 건너뛰기만 하고 **아무것도 놓지
않았다**.  벽에 구멍이 뚫린 집이다.  결과가 두 겹이었다:

- 보이는 것: 사람이 사는 집에 문이 없다
- 안 보이는 것: 방이 밀폐가 아니라 자동 지붕이 안 붙는다 → 지붕·침대 3개가 다 있는
  집 옆에 `0/3` 이 떠 있는 **자기모순 화면**

게다가 자동 지붕(`TryAutoRoofEnclosedFrom`)은 **플레이어가 지붕을 칠할 때만** 불렸다.
레퍼런스 동작은 "벽으로 닫히면 덮인다" 이다 — 방을 다 지어도 지붕이 안 생기고, 플레이어는
튜토리얼이 언급조차 하지 않는 U 키 지붕 도구를 스스로 발견해야 했다.

→ 문간에 실제 `DoorEntity` 배치 + 벽/문 완공 시 밀폐 판정(`NotifyWallBuilt`, 0.4초
코얼레싱) + 시작 집은 침대 칸에서 역으로 찾아 즉시 지붕(`RoofEnclosedInstant`).
좌표를 박지 않고 침대에서 찾는 이유: 집이 옮겨지거나 세이브에서 복원돼도 따라온다.

**함정 하나 더**: 1차 구현은 `yield return new WaitForFixedUpdate()` 로 물리 동기화를
기다렸는데, 이 게임은 **일시정지(timeScale 0)로 부팅**한다.  timeScale 0 이면 FixedUpdate 가
돌지 않아 코루틴이 영원히 그 자리에 선다 — 로그 한 줄 없이.  `yield return null` +
`Physics2D.SyncTransforms()` 로 교체.

### ③ 아무도 연구를 안 했다 (HUD: "연구자 없음")
`ApplyDefaultsFromSkills` 의 마지막 `else p = 4` 가 **전원에게 연구 최하 우선순위**를 준다.
운반이 3 이라 늘 위에 있고 바닥의 더미는 마르지 않는다 → 연구 차례가 영영 안 온다.

→ 창립 시 **연구 담당 1명 지명**(육체 숙련 합이 가장 낮은 림, 동점은 이름 순으로 결정성
확보).  기본 규칙은 그대로 둔다 — 전원에게 연구 2를 주면 이번엔 아무도 운반을 안 한다.
부수효과로 직업 탭 3열이 서로 달라진다(= 간접 조작의 근거 화면).

### ④ 연구 진행 판정이 "근처에 서 있기만 하면" 이었다
`ResearchBench.ResearcherSpeedSum()` 은 반경 안의 **살아있는 폰 전부**를 셌다.  시작 집
안에 연구대가 있으니 사실상 "실내에 있으면 연구 중"이다.  ③을 고친 뒤 40/100 이 나왔지만
그 대부분은 담당자 덕이 아니었다.

동시에 머리 위 라벨은 `정지 + 벤치 반경`을 요구해서, 벤치 옆에서 한 발짝만 움직여도
"떠도는중"으로 떨어졌다 — **진행도는 오르는데 라벨은 떠돈다고 하는 화면**.

두 판정 다 작업 배정과 무관한 위치 기반 추정이었고, 더 나쁜 것은 직업 탭의 '연구' 열이
결과를 못 바꾼다는 점이다(누가 맡든 같으면 그 열은 장식).

→ `PawnResearchWork` 도장 하나를 정본으로.  `DoResearchAction` 이 찍고, 진행도와 라벨이
**둘 다 그 도장만** 본다.  판정을 정직하게 좁히자 40 → 5/100 로 떨어졌다 — 그게 진짜 값이다.

### ④-B 튜토리얼 ②(집 짓기)는 **한 번도 뜨지 않았다**

심사자 흐름(52초 데모 시나리오)을 그대로 돌려 보고 잡았다.  안내가 ①에서 곧장 ③으로
넘어가 있었다 — 건축 단계가 화면에 뜬 적이 없다.

`Gate.House` 조건이 "벽 또는 청사진이 **하나라도 있으면**"이었는데, **시작 정착지의
집에 이미 벽이 있다**.  단계에 진입하는 순간 충족돼 즉시 넘어간다.

이건 오늘 세 번째 같은 함정이다.  저장구역 게이트(2026-07-27)와 벌목 게이트(같은 날)가
정확히 같은 이유로 건너뛰어졌고 각각 기준선 비교로 고쳤는데, **집 게이트만 남아 있었다**.
공통 원인은 하나다 — 시작 정착지를 넣으면서 "존재하면 통과" 류 조건이 전부 무력화됐다.

→ 같은 기준선 패턴 적용: 단계 진입 시점의 (벽 수 + 청사진 수)를 기록하고 그보다 늘어야
통과.  청사진은 완공되면 사라지고 벽이 늘어나므로 **합**을 세야 짓는 도중에 값이 줄어
게이트가 도로 닫히지 않는다.

수정 후: ① 벌목 → **② 집** → ③ 농장 순서가 실제로 보인다.  정착 목표(목재 → 잠자리 →
연구)와 같은 축이라는 원래 설계가 이제야 성립한다.

> 규칙이 반복되면 **그 규칙을 쓰는 곳 전부를 한 번에 훑어야 한다.**  같은 함정을 세 번
> 따로 밟았다.

### ⑤ 튜토리얼 ③이 영원히 안 넘어갔다
`Gate.Farm` 은 `GrowZoneDesignation.ZoneCellCount > 0` 을 요구하는데 시작 밭은
`CropEntity` 로 직접 깔려서 이 카운트에 안 잡힌다.  **아무리 기다려도 충족되지 않는
단계**가 월드를 계속 가렸다.  문구도 모순이었다 — 화면에 밭이 보이는데 "농사 지을 땅을
지정하세요".

→ 게이트 타임아웃 45초(게임이 실제로 돌 때만 카운트 — 일시정지로 부팅하므로 실시간으로
세면 둘러보는 동안 팁이 소진된다) + 문구를 "밭을 더 넓히면 식량이 늘어납니다"로.

행동 기반 온보딩에는 **"플레이어가 그 행동을 영영 안 하면?"** 이라는 출구가 필요하다.
안내는 권유지 관문이 아니다.

### ⑥ 할 일이 떨어지면 콜로니가 통째로 멈췄다
활동 라벨을 켜고서야 실체가 보였다 — 오후 1시에 **세 명 전원 "떠도는중"**.

자율 작업이 전부 전제를 갖고 있다: 벌목·채광은 플레이어 지정, 건설은 청사진, 운반은 바닥
더미, 요리는 식량 여유, 수확은 익은 작물, 연구는 담당자.  그래서 플레이어가 찍어 준 나무를
다 베면 **말 그대로 할 일이 없다**.  콜로니 심에서 사람이 멍하니 서 있는 화면은 "AI가
죽었다"로 읽힌다.

→ `GatherBerryAction` 신설 (콜로니 식량이 목표선 아래면 채집 — 맵에 항상 있고, 식량은 항상
줄고, 결과가 눈에 보인다).  그리고 `JoyAction` 배선 — **파일에 작성돼 있었지만 액션 목록에
없었다**(오늘 다섯 번째 '조용한 미배선').  이제 여가 시간대에 모닥불가로 모인다.

둘 다 목록 최하단이다.  전에 무기 제작을 위로 올렸다가 지정한 나무를 아무도 안 베는 회귀를
냈다(`p0-remote-chop`) — **플레이어가 손으로 찍은 일이 자율 작업보다 먼저다**.

## 3. 가장 큰 한 방: 활동 라벨을 전원 상시로

운영자의 "뭐 하고 있는건지 모르겠음"에 대한 직접 답이다.

정보는 **이미 매 0.25초 계산되고 있었다**(`lastComputedStatus`).  막고 있던 건 게이트
두 개뿐:

- `IsSelectedPawn()` — 선택해야만 보임.  영상·첫인상에서는 아무도 선택돼 있지 않다
- `ortho < lodNameOnly(10)` — 기본 줌이 15 라 어차피 숨김

파일 상단 주석에 `운영자 2026-06-02: "림이 머하는지 머리위에 항상"` 이 이미 적혀 있었다.
원래 요구였고 구현이 그 뒤 선택 전용으로 좁혀져 있었다.  요구대로 되돌렸다.

부수 작업 둘:
- `"운반"` → `"목재 운반"` (`PawnHauler.HaulKindKr`).  무엇을 옮기는지가 빠지면 여전히
  '왔다갔다'로 읽힌다
- 라벨 스태거 2단(0.18) → 3단(0.42).  라벨이 2줄이 되면서 한 덩이 높이(≈0.34)보다 단
  간격이 작아, 집 안에 모인 세 명의 4줄이 서로 겹쳐 판독 불가한 덩어리가 됐다

**이 변경의 진짜 가치는 표시가 아니라 진단이다.**  라벨을 켜자마자 ⑥(전원 유휴)이 드러났다.
보이지 않던 것은 고쳐지지 않는다.

## 4-B. 연구가 느린 진짜 이유 — 연구자가 책상에 못 앉아 있었다

④를 고쳐 판정을 정직하게 좁힌 뒤 연구는 하루 24pt 였다.  첫 테크(100pt)에 4일이 걸려
"연구 1개 완료"는 여전히 사실상 도달 불가였다.  그래서 속도를 0.15 → 0.25 로 올렸는데,
**산출이 오히려 24pt → 11pt 로 줄었다.**

속도를 올렸는데 산출이 줄면 배정이 아니라 **체류**가 문제다.  원인은
`PawnUtilityAI.HasRealActivity()` 였다:

```csharp
if (chopper != null && chopper.HasTask) return true;
if (gatherer  != null && gatherer.HasTask)  return true;
... 9개 워커 전부 ...
return false;                     // ← 연구는 여기로 떨어진다
```

**연구는 워커 컴포넌트가 없는 유일한 작업이다.**  그래서 연구 중인 림이 '유휴'로
분류됐고, 유휴로 분류되면 아래의 idle pacing 이 0.8초마다 근처 타일로 hop 시킨다 —
그게 연구자를 **연구대 반경 밖으로 끌어냈다**.  진행도는 반경 안에서만 쌓이므로,
연구자는 앉았다 나갔다를 반복했다.

이전의 24pt 가 더 컸던 것도 같은 그림이다 — 그때는 '반경 안 아무나' 계산이라 **배회하던
다른 림들**이 우연히 채워 준 값이었다.  판정을 실제 담당자로 좁히자 배회 문제가 그대로
드러난 것이다.  즉 ④의 수정이 이 버그를 만든 게 아니라 **가리고 있던 것을 걷어냈다**.

→ `HasRealActivity()` 에 `researchWork.IsResearching` 추가.

| | 오후 1:22 | 밤 8:38 |
|---|---|---|
| 배회 수정 전 | 4/60 | 11/60 |
| 배회 수정 후 | **17/60** | **완료 ☑ → 다음 테크 8/120** |

첫 연구가 **첫 게임일 안에** 끝난다.  온보딩으로서 맞는 페이싱이고, "연구 1개 완료"
목표가 처음으로 실제 도달 가능해졌다.

교훈: **일반 규칙을 만들 때는 그 규칙의 예외가 되는 항목부터 찾는다.**  9개 워커를
나열하는 코드는 "워커가 없는 작업"을 조용히 빠뜨린다.

## 4-C. 게이트는 정밀해야 한다 — "지정이 있으면 전원 대기"의 부작용

§5 의 회귀를 막으려고 `GatherBerryAction` 에 "플레이어 지정이 남아 있으면 채집 금지"를
걸었더니, 나무 **한 그루**를 찍었을 때 한 명이 그것을 맡고 **나머지 두 명이 채집도 않고
서 있었다**.  이미 남이 맡은 일까지 기다린 것이다.

→ 각 작업 액션의 **자기 탐색기를 재사용**한다.  그 탐색기는 이미 '지정됐고 + 다른 폰이
예약하지 않은' 대상만 돌려주므로, non-null 이면 "내가 지금 착수할 수 있는 지시가 실재한다"
는 뜻이다.  판정을 복제하지 않으니 예약 규칙이 바뀌어도 두 곳이 갈라지지 않는다.

```csharp
if (ChopTreeAction.FindFreeMarkedTree(ctx) != null) return false;
if (MineStoneAction.FindFreeMarkedVein(ctx) != null) return false;
return BuildBlueprintAction.FindFreeBlueprint(ctx) != null;
```

## 4-D. 라벨에서 '떠도는중'을 지웠다

활동 줄을 키우고 나니 이번엔 세 명이 한 방에 모일 때 '떠도는중'끼리 겹쳐 판독 불가한
덩어리가 됐다.  **정보가 없는 글자가 정보가 있는 글자를 가리는** 최악의 조합이다.

유휴는 적지 않는다.  그러면 떠 있는 라벨은 전부 실제 노동이 되어 화면이 스스로 설명한다.
(유휴 여부는 선택 시 인포 패널에서 여전히 확인된다.)

다만 **여가 시간대는 예외로 이름을 준다** — 일정표가 '여가'인 동안 모닥불가로 모이는 것은
배회가 아니라 일정에 따른 행동이다.  아무것도 안 적으면 "왜 다들 노나"로 읽히지만,
`여가` 라고 적으면 그 장면에 이유가 생기고 플레이어는 F4 로 바꿀 수 있다는 것도 안다.

## 5. 회귀 하나 — "목록 아래에 뒀는데 왜 먼저 하지?"

`GatherBerryAction` 을 액션 목록 **최하단**에 두었는데도 `p0-remote-chop` 이 깨졌다:
나무를 지정하고 30초가 지나도 아무도 '벌목'을 시작하지 않았다(나무는 나중에 베이긴 했다 —
246→245 라 "동작은 한다"로 착각하기 쉬운 실패다).

원인은 `PawnUtilityAI.Decide()` 의 구조다:

```
for p in 1..4:                      # ← 우선순위 밴드가 바깥 루프
    for action in actions:          # ← 목록 순서는 안쪽 루프
        if workSettings.GetPriority(action.Kind) != p: continue
        if action.TryStart(ctx): return
```

즉 **밴드가 목록 순서를 앞지른다**.  `GatherBerryAction.Kind` 는 `Gather` 이므로,
채집 숙련이 높아 `Gather=1~2` 인 림에게는 `Chop=3~4` 인 벌목보다 **앞선 밴드**에서
집힌다 — 목록의 몇 번째에 있든 무관하다.

이전에 무기 제작으로 같은 회귀를 냈을 때는 목록 순서를 내려서 막았고, 그래서 "아래에
두면 안전하다"는 잘못된 규칙이 머리에 남아 있었다.  **Kind 가 다르면 목록 순서는 보호
장치가 아니다.**

교정: 규칙을 위치가 아니라 **상태**로 표현한다.

```csharp
if (HasPendingPlayerOrders()) return false;   // 지정된 벌목·채광·청사진이 남아 있으면 자율 비축 노동은 쉰다
```

개인 허기로 발동하는 `EatBerryAction` 에는 이 게이트를 걸지 않는다 — 굶는 것은 지시
이행보다 먼저다.  막는 것은 **여유 있을 때의 비축 노동**뿐이다.

수정 후: 지정 3.5초 만에 '벌목' 관측 (이전 30초 내 0회).

### 5-B. 같은 함정이 한 번 더 — 이번엔 운반

게이트를 정밀화하고 나니 `p6-objectives` 가 깨졌다: 나무는 베었는데 **아무도 나르지 않아**
목재 카운터가 400 에 닿지 못했다.  바닥엔 목재가 널려 있는데 셋 다 베리를 따고 있었다.

원인은 §5 와 **정확히 같다**.  운반은 `Haul`(기본 3), 채집은 `Gather`(숙련 높으면 1~2).
목록에서는 운반이 위에 있지만 밴드가 순서를 앞지른다.

그리고 이 원칙은 이미 코드에 **글로 적혀 있었다** — `PawnUtilityAI` 액션 목록 주석:

> 떨어진 더미가 적립 전에 부패(옥외 30s/-1)하지 않도록, 줍을 더미가 있으면
> 새 채집/벌목보다 운반을 먼저 한다.

의도는 옳았고 **집행 수단만 틀렸다**(목록 순서).  같은 게이트에 운반 3종을 추가해
밴드 너머로 강제한다.  함수 이름도 `HasClaimablePlayerOrder` → `HasWorkThatComesFirst`
로 바꿨다 — 운반은 플레이어 지시가 아니므로 이름이 내용을 속이면 안 된다.

> **주석에 적힌 원칙은 검증되지 않는다.**  이 프로젝트에서 오늘만 세 번째다
> (목재 200 · 나무 minBright 0 · 운반 우선).  주석이 규칙을 서술하고 있으면
> 그 규칙이 **코드로 강제되고 있는지**를 따로 확인해야 한다.

## 6. 재발 방지로 남기는 것

1. **"만들었는데 목록에 없다"** — 오늘만 `JoyAction` 1건, 앞선 세션에서 4건.
   `PawnUtilityAI.HasRegisteredAction` 회귀 가드가 있지만 신규 액션마다 테스트를 안 쓴다.
   → 액션 클래스를 추가하면 등록까지가 한 작업이다.
2. **"주석은 아는데 값은 안 고쳐진"** — `WoodGoal 200`, 나무 `minBright 0`, 연구 else 4.
   주석이 문제를 서술하고 있는데 숫자는 그대로인 경우가 반복된다.
3. **조용한 실패 금지** — 지붕 코루틴이 `WaitForFixedUpdate` 에서 멈췄을 때 로그가 한 줄도
   없었다.  이제 실패 경로마다 이유를 찍는다(`밀폐 아님 (x,y) — 벽셀=/불통과=`).
4. **일시정지로 부팅하는 게임의 코루틴은 `WaitForFixedUpdate`/`WaitForSeconds` 를 쓰면
   안 된다.**  `yield return null` 만 정지 중에도 진행한다.
5. **검증은 스크린샷을 사람이 읽는다.**  probe 로 숫자만 통과시키면 "테스트는 PASS 인데
   화면은 그대로"가 또 난다 — 오늘도 `OVERALL: PASS` 인 채로 지붕이 0/6 이었다.
6. **액션을 추가할 때는 `Kind` 의 우선순위 밴드를 먼저 본다** (§5).  목록 위치는
   같은 밴드 안에서만 의미가 있다.
7. **나열식 규칙(`if A || B || ... || I`)을 쓰면 그 목록의 예외부터 찾는다** (§4-B).
   `HasRealActivity()` 는 워커 9종을 나열했고, 워커가 없는 유일한 작업인 연구가
   조용히 '유휴'로 떨어져 연구자를 책상에서 끌어냈다.
8. **속도를 올렸는데 산출이 줄면 배정이 아니라 체류를 의심한다** (§4-B).
   숫자를 더 올리는 쪽으로 대응했으면 원인은 그대로 남았을 것이다.
9. **개발 플랫폼이 관대하면 배포 플랫폼에서 터진다** (§6-C).  Windows 는 없는
   글리프를 OS 폰트로 메워 주고 WebGL 은 안 메운다 — 개발 중 멀쩡해 보이는 것이
   제출물에서 사라지는 전형이다.  "제출물이 도는 곳"에서 한 번은 봐야 한다.
10. **검사 스크립트를 만들었으면 실행 경로에 넣는다** (§6-C).  `☐/☑` tofu 는
   `check-font-coverage.py` 가 잡도록 만들어진 바로 그 결함인데, 목표 패널을 추가할
   때 아무도 돌리지 않아 다시 들어왔다.  존재하는 검사와 **도는** 검사는 다르다.

## 6-B. 공개 URL 을 실제로 열어 보고 잡은 것

게이트 22/22 PASS 이후, 배포된 URL 을 브라우저로 직접 열었다 (`live-verification`
회차와 같은 절차 — "판정의 층을 하나 더 둔다").  게임 내용은 전부 정상이었다:
지붕 아래 잠자리 3/6 · 가치 270 (습격 규모) · 연구 원시 활 0/60 · 문과 지붕이 있는 집.

**대신 페이지가 문제였다.**  Unity 기본 WebGL 템플릿의 데스크톱 경로는 캔버스를
`960x600` 으로 **고정**한다:

```js
canvas.style.width  = "960px";
canvas.style.height = "600px";
```

그래서 공개 URL 을 열면 흰 여백 한가운데에 작은 상자로 게임이 떴다 — 실측(1253px
뷰포트)에서 게임이 화면의 1/3 도 못 채웠다.  게임을 아무리 고쳐도 첫인상은
"작은 창에서 도는 데모"다.

고치는 자리를 **배포 스크립트**로 잡았다.  Unity 템플릿 수정은 재빌드(수 분)를
요구하는데, 이건 게임이 아니라 **배포 표현**의 문제다.  `<title>` 을 게임 이름으로
바꾸는 후처리가 이미 같은 자리에 있었다 — 같은 이유, 같은 층.
패턴이 안 맞으면 조용히 넘어가지 않고 배포 로그에 경고를 남긴다.

같은 스크립트에서 **배포를 파괴할 수 있는 버그**도 하나 나왔다.  `rm -rf "$DEST"` 가
Windows 에서 폴더 핸들이 잡혀 있으면 `Device or resource busy` 로 실패하는데, 그 시점엔
**내용물이 이미 지워진 뒤**라 배포본이 빈 채로 남는다(실제로 한 번 당했다).
디렉터리 자체를 지우지 않고 내용만 비우도록 바꿨다.

> 이 회차의 교훈은 지난번과 같다 — **산출물을 받는 사람이 보는 것**을 기준으로 한 층을
> 더 둬야 한다.  로컬 게이트는 "게임이 옳게 도는가"만 말하고, "게임이 어떻게 보이는가"는
> 말하지 않는다.

### 6-B-2. 멈춘 화면에서 "나무를 우클릭하라"고 말하고 있었다

같은 브라우저 확인에서 두 번째 것이 나왔다.  게임은 **일시정지 상태로 부팅**하는데,
화면에는 지시가 둘 동시에 떠 있었다:

- 하단 배너(주 안내): `① 일감 지정: 나무를 우클릭 → 벌목`
- 우상단 카드(작은 알림): `일시정지 — 둘러보고 1배속으로 시작하세요`

지시대로 나무를 찍으면 지정은 되지만 **아무도 움직이지 않는다**.  첫 30초에
"고장난 게임"으로 읽히는 조합이다.

원인은 한 프레임짜리 경합이다.  `GameManager.PauseAtStart` 는 `TimeController` 부트를
기다리느라 **1프레임 뒤에** `timeScale = 0` 을 건다.  그런데 `TutorialOverlay.Update`
는 그 전 프레임에 이미 돌면서 기본값 `timeScale = 1` 을 보고 `Gate.Unpause` 를
충족시킨다 → 일시정지 안내 단계가 **매번 100% 건너뛰어졌다**.

이 게이트는 원래 `sawPause` 를 요구했는데, 정지를 안 쓰는 세션(하네스)에서 팁이
영원히 고정되는 버그 때문에 2026-07-24 에 제거됐다.  그 수정이 반대쪽 구멍을 냈다.

교정: **정지가 걸릴 기회를 준 뒤에** 판정한다 — 부팅 후 1.5초 창 동안은 판단을 미루고,
그 안에 정지를 봤으면 진짜 재개될 때까지 기다리고, 창이 지나도록 정지가 없었으면
정지를 안 쓰는 세션으로 보고 종료한다.  양쪽 세션이 모두 옳게 동작한다.

> **"A 때문에 조건을 뺐다"는 수정은 B 를 깬다.**  조건을 없애는 대신, A 와 B 를
> 가르는 관측(여기서는 '정지가 걸릴 시간을 줬는가')을 추가해야 했다.

## 6-C. 오늘의 최대 발견 — 라벨이 **제출 플랫폼에서만** 존재하지 않았다

§3 에서 "가장 큰 한 방"이라고 쓴 활동 라벨을, 배포 후 공개 URL 에서 다시 확인했다.

**하나도 렌더되지 않았다.**  이름도, 활동도.  Windows 빌드의 같은 줌·같은 장면에서는
"민지 / 서연 / 지훈"이 선명하게 뜨는데(대조 스크린샷 확보), WebGL 에서는 콜로니스트
머리 위가 완전히 비어 있었다.

UI(Canvas) 텍스트 — 자원 패널·정착 목표·튜토리얼 — 는 한글이 멀쩡했다.  그래서
"폰트가 빌드에 없다"는 아니었다.

원인: `PawnNameLabel` / `FloatingText` 가 `TextMesh` 에 **폰트를 아예 지정하지 않고**
Unity 기본 폰트(Arial/LegacyRuntime)를 쓰고 있었다.

- **Windows**: 기본 폰트에 없는 글리프를 **OS 폰트로 대체**해 준다 → 한글이 나온다
- **WebGL**: OS 폰트 접근이 없다 → 한글만 **통째로 빈다**

그리고 이 사실은 이미 코드에 적혀 있었다.  `UITheme.LoadKoreanFont` 첫 줄 주석:

> WebGL 은 OS 폰트 접근이 없어 번들 폰트(Noto Sans KR, OFL)가 유일한 한글 경로.

**주석은 알고 있었고, 월드 라벨들이 그 경로를 쓰지 않았다.**  오늘만 이 유형 네 번째
(목재 200 · 나무 minBright 0 · 운반 우선 · 그리고 이것).

이 결함으로 제출 플랫폼에서만 사라져 있던 것:
- 콜로니스트 이름 + 활동 라벨 (= 오늘 작업의 핵심)
- 산출 플로팅 텍스트 (`+27 목재`)
- 정착 목표의 체크박스 `☐`/`☑` — 이건 **번들 폰트 3종 어디에도 없는 글리프**라
  tofu 였다 (아래 참조)

`TreeChopDesignation` 과 `MineDesignation` 은 이미 번들 폰트를 쓰고 있었다 — 즉 같은
파일군 안에서도 어떤 곳은 맞고 어떤 곳은 틀렸다.  개별 수정은 이렇게 남는다.

### 고친 방법 + 재발 방지

1. `UITheme.ApplyKoreanFont(TextMesh)` 헬퍼로 단일화.
   ⚠ `tm.font` 만 바꾸면 안 된다 — TextMesh 는 폰트를 바꿔도 렌더러 머티리얼을 따라
   바꾸지 않아 아틀라스가 어긋난다.  `sharedMaterial` 로 함께 넣는다
   (`material` 은 라벨마다 사본을 만들어 드로우콜이 콜로니스트 수만큼 는다).
2. **정적 검사 추가** (`check-font-coverage.py` 2번째 절): `AddComponent<TextMesh>()`
   하는 곳이 번들 폰트를 지정하는지 본다.  즉시 `PawnNeeds.cs:709` 를 잡았다.
3. 같은 검사가 **`☐`/`☑` 가 번들 폰트 3종 어디에도 없다**는 것도 잡았다.
   이 tofu 검사는 `✕ U+2715` 사고 뒤에 만들어진 것인데, 정착 목표 패널을 추가할 때
   **아무도 돌리지 않아** 같은 유형이 다시 들어왔다.  `■`/`□`(U+25A0/U+25A1)로 교체 —
   3종 모두에 있다.
4. 검사 스크립트 자신의 조기 반환 버그도 고쳤다.  2번째 검사를 tofu 리포트 **뒤에**
   두었더니, tofu 가 없으면 `return 0` 으로 빠져 **2번째 검사가 실행되지 않았다** —
   하루 종일 잡아 온 '조용한 미실행'을 검사 스크립트가 그대로 재현할 뻔했다.

> **로컬 게이트 22/22 초록은 "제출물이 옳다"를 뜻하지 않는다.**  게이트는 Windows
> 실행 파일을 본다.  제출물은 WebGL URL 이다.  두 플랫폼이 갈라지는 지점(OS 폰트
> 대체·스레드·타이밍)에서는 **초록불이 오히려 눈을 가린다** — 문제가 없다고 말해
> 주기 때문이다.

## 7. 게이트 도구 자체의 버그 2건 (오늘 함께 고침)

게이트를 처음 돌렸을 때 **22/22 STALE** 이 나왔다 — 한 시나리오도 실행되지 않았다.
같은 빌드로 `repro_run` 을 직접 부르면 정상 실행되는데도.

1. **`repro_all` 이 `--build` 를 상대 경로 그대로 넘겼다.**  하위 프로세스는
   `cwd=scripts/` 에서 도는데 운영자는 레포 루트 기준 경로를 준다 → 자식에선 그 파일이
   없다 → `repro_run` 이 "사용 가능한 빌드 없음"으로 즉시 종료 → 게이트는 STALE 로 집계.
   → `Path(...).resolve()` 로 절대화해서 전달.

2. **stale 판정이 빌드 *디렉터리* 의 mtime 을 봤다.**  디렉터리 mtime 은 항목이
   추가/삭제될 때만 갱신되는데, Unity 재빌드는 기존 파일을 **제자리에서 덮어쓴다**.
   그래서 같은 day 폴더로 두 번째 빌드를 한 순간부터 **영구 STALE** 이었다
   (실측: `Assembly-CSharp.dll` 04:09 / 디렉터리 00:08).
   `PawnSim.exe` 도 기준이 될 수 없다 — 런처 스텁이라 코드가 바뀌어도 내용이 같으면
   Unity 가 다시 쓰지 않는다.  이 빌드가 담은 C# 코드를 대표하는 것은
   `PawnSim_Data/Managed/Assembly-CSharp.dll` 하나뿐이다.
   → 그것과 `Assets/Scripts` 를 비교하도록 교정.

**안전장치가 조용히 꺼져 있으면 없는 것만 못하다** — 이 두 버그 때문에 게이트는
"통과"도 "실패"도 아닌 상태로 며칠간 아무것도 검증하지 않고 있었을 수 있다.
